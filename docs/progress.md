## 3. 작업 방식

**로컬에 .NET SDK가 없다.** 컴파일·테스트·패키징은 전부 GitHub Actions에서 돈다. 그래서 흐름은
`작업 → 커밋 → 푸시 → CI 로그 읽기 → 고치기` 이고, 푸시가 곧 컴파일이다. `gh` 인증은 저장소
루트 `.env` 의 `GH_PAT` 를 쓴다 — 자세한 것은 [`../CLAUDE.md`](../CLAUDE.md) 2절.

각 마일스톤은 **CI가 초록불이 되는 것**으로 닫힌다. 완료 기준은 수치 하나로 못 박되,
그 수치는 환경에 흔들리지 않는 것을 고른다(4.4, 5.4 참조).

## 4. M3 — 캔버스

**범위**: 뷰포트·줌·팬·변환 핸들·스냅·가이드·선택 영역.

### 4.1 핵심 아이디어: 화면은 문서에 배율과 평행이동을 건 것

문서의 한 화면은 문서에 **균일 배율 + 평행이동**을 건 것이고, 그렇게 옮긴 배치(`LayerTransform`)
는 여전히 배치다 — 상자만 커지고 이동할 뿐 회전과 뒤집기는 변하지 않는다(균일 배율은 제 중심을
도는 회전과 교환된다). 그래서 `CanvasProjection` 하나로 **합성기 전체를 화면에 그대로 재사용**
한다. 폴더·클리핑 그룹·마스크 처리를 화면용으로 다시 쓰지 않았다.

균일 배율만 자격이 있다. 축마다 다른 배율은 회전된 레이어를 기울이는데(shear) `LayerTransform`
이 표현할 수 없고, 그런 줌도 없다.

### 4.2 만든 것

| 구성 | 내용 |
|---|---|
| 뷰포트 | 줌 0.001~32, 팬, 맞춤, 포인터 고정 줌, 표시 영역, 프레임 비용 계산 |
| 변환 | 핸들 8개 + 회전 핸들, Shift/Alt/비율 잠금, 여러 레이어 동시 변환 |
| 디스토트 | Ctrl+핸들 → 네 꼭짓점 자유 이동, 놓을 때 픽셀 리샘플 |
| 스냅 | 캔버스·타 레이어의 가장자리와 중심, 축별 독립, 화면상 10pt 고정 |
| 선택 영역 | 사각형·타원·올가미(자유·다각형), 더하기/빼기, 스캔라인 커버리지 |
| 셸 | 휠 줌, 스페이스·가운데 팬, Alt 복제, 방향키 이동, Ctrl+0/1·Z/Y·A/D |

### 4.3 설계 판단

1. **선택 영역은 단계를 순서대로 보관한다.** 원본은 모든 경로를 하나로 합쳐 winding 규칙으로
   채운다. 더하기에는 맞지만 빼기에는 틀린다 — 뒤집힌 외곽선은 겹치는 곳에서 상쇄되고
   **겹치지 않는 곳에서는 선택해 버린다.** 그래서 선택에서 벗어난 곳으로 뺄셈을 끌면 지우려던
   것이 선택된다. 단계를 순서대로 두고 커버리지를 결합하면 양쪽 다 정확하다.
2. **`IsValid` 를 그리기 판정에 쓰면 안 된다.** 그건 포맷이 *저장*을 허락하는 범위(최소 1픽셀)
   이고, 줌아웃하면 100픽셀 레이어가 0.1픽셀이 된다. 그리기용 `IsDrawable` 을 따로 뒀다.
   그러지 않으면 **줌아웃할수록 작은 레이어부터 사라진다.**
3. **디스토트만 픽셀을 건드린다.** 숫자 여섯 개는 투영 사상을 담을 수 없다. 드래그 중에는
   윤곽만 보여주고 놓는 순간 리샘플해 다시 평범한 직립 레이어로 만든다. 나비넥타이로 접힌
   사각형은 사상이 성립하지 않아 거부한다.
4. **면(surface)이 클립을 배웠다.** 문서 크기 면에서는 가장자리가 공짜로 잘라 줬지만 창에서는
   아니다. 클립 경계는 정수 픽셀로 반올림한다 — Direct2D의 aliased 클립과 소프트웨어 백엔드가
   같은 픽셀에 떨어져야 하기 때문이다.

### 4.4 완료 기준을 바꾼 이유와 측정

원래 기준은 "1억 픽셀에서 60fps"였는데 CI에서 증명할 수 없다(1절 주의 참조). 60fps가 실제로
요구하는 것은 기계의 속도가 아니라 **프레임의 작업량이 문서가 아니라 창에 비례한다**는 성질
이므로, 그것을 수치로 고정했다.

| 항목 | 값 |
|---|---|
| 문서 / 창 | 1억 / 102만 픽셀 (문서가 창의 98배) |
| **한 프레임이 읽는 픽셀** | **156만 = 창의 1.53배** (판정선 4배) |
| 프레임 시간 (맞춤 / 100%) | 45 ms / 4.5 ms |

피라미드가 3단계 축소해 읽을 양을 64분의 1로 줄이기 때문이다. 문서를 9억 픽셀로 키우면 축소
단계가 하나 더 늘어 이 비율은 오히려 **줄어든다**. 테스트가 1,000²·10,000²·30,000²에 대해
이 한 줄을 고정한다.

### 4.5 이 과정에서 고친 것

- **Direct2D가 매 프레임 레이어 전체를 업로드하고 있었다.** M2의 백엔드는 `Materialize` 로
  레이어를 통째로 꺼내 GPU에 올리고 리샘플을 맡겼다. 1억 픽셀이면 **프레임당 400MB**다.
  위에서 아무리 창 크기로 합성해도 이 한 줄이 남아 있으면 의미가 없다. 두 백엔드가 이제 같은
  순서로 움직인다 — 목적지 영역 → 그것을 먹이는 원본 영역 → 그만큼만 꺼내 축소해 업로드
  (`LayerGeometry` 공유). 업로드는 (버퍼·레벨·영역)으로 캐시한다.
- 벤치가 "프레임을 그리는 시간"이 아니라 "프레임을 기술하는 시간"을 재고 있었다. Direct2D는
  드라이버에 넘기고 바로 돌아오므로, 면을 읽어 강제로 통과시킨 뒤에 시계를 멈춘다.

### 4.6 미룬 것

투명 격자(체커보드)와 선택 영역 점선 애니메이션은 M6, 조정 레이어 적용은 M5.
디스토트의 라이브 픽셀 프리뷰도 M5로 넘겼다 — **M5에서 했다**(6.2).

## 5. M4 — 도구

**범위**: 브러시·힐링·클론·블러·그라디언트·셰이프·마술봉, C 커널 연결.

### 5.1 핵심 아이디어: 도구는 레이어 자기 픽셀 격자에서 일한다

문서 픽셀이 아니다. 3분의 1로 줄여 놓은 레이어는 화면에서 3분의 1 크기 브러시로 칠해지고 제
raster에는 원래 크기 자국이 남는다. 그래야 칠하기가 비파괴 배치(설계 §2.1)와 충돌하지 않는다.
선택 영역은 문서 공간에 살므로 **도구로 들어갈 때 레이어 픽셀로 옮기고 마술봉 결과는 반대로
옮긴다.** 배치는 아핀이라 이 변환은 정확하다(`LayerGeometry.ToPixels` / `ToDocument`,
`DocumentSelection.Transformed`).

### 5.2 만든 것

| 도구 | 구현 |
|---|---|
| 브러시·지우개 | 크기·경도·불투명도, Shift 8방향 직선, 대괄호 키로 크기 |
| 스팟 힐링 | `HealPixels.c` 3모드(내용 인식·텍스처 생성·근접 일치) |
| 복제 도장 | Alt로 원본 지정, 정렬/비정렬 |
| 흐리게 | 타일마다 여백 포함 박스 블러 2회 |
| 그라디언트 | 선형·방사형 |
| 셰이프 | 사각형·둥근 사각형·타원 — 포맷의 `ShapeKind`+`cornerRadius` 그대로 |
| 마술봉 | `WandPixels.c` 매칭 + 외곽선 추적 → 선택 영역 |
| 내용 인식 채우기 | `ContentFill.c` (Core에만, 메뉴는 M6) |
| 선택 영역 | 픽셀 이동·복제, 다각형 올가미 |

### 5.3 설계 판단

1. **불투명도는 점(dab)이 아니라 스트로크 전체의 상한이다.** 지름 40 브러시는 0.6픽셀마다 점을
   찍으므로, 점마다 합성하면 같은 자리를 천천히 지나간 획이 빨리 지나간 획보다 진해진다.
   점은 **커버리지에** 누적하고(단단한 팁 lighten, 부드러운 팁 screen) 픽셀 합성은 타일을 다시
   만들 때 한 번만 한다.
2. **힐링은 레이어를 통째로 커널에 주지 않는다.** 칠한 영역 + 패치 탐색이 실제로 닿는 거리
   (약 3 스팟 너비)만 잘라서 준다. 더 좁으면 잡티를 고치려는데 잡티만 찾게 되고, 더 넓으면
   1억 픽셀을 읽는다. 커널이 보는 것은 **원래 픽셀**이지 칠하는 동안 보이던 어두운 자국이 아니다.
3. **선택 영역 픽셀 이동은 "떠 있는 상태"를 만들지 않는다.** 원본은 픽셀을 띄웠다가 선택을 풀 때
   합친다. 여기서는 드래그가 끝날 때 한 번에 처리한다 — 결과가 같고, 포맷이 저장할 수 없는
   상태가 히스토리에 들어가지 않는다. 반쯤 선택된 픽셀은 반만 들리고 반만 내려앉으므로
   부드러운 가장자리가 잘린 가장자리로 바뀌지 않는다.
4. **셰이프는 포맷의 어휘로 말한다.** `.comp` 에는 shape kind가 둘(사각형·타원)과 corner radius
   가 있다. 그래서 둥근 사각형은 여기서도 "반지름이 있는 사각형"이다 — 저장된 셰이프 레이어를
   새 크기로 다시 그릴 때 별도의 열거형을 거치지 않는다.
5. **셰이프와 선택 영역은 같은 래스터라이저를 쓴다.** 셰이프 도구로 그린 원과 타원 마퀴로 고른
   원이 "원이 어디인가"에 대해 같은 답을 낸다.

### 5.4 완료 기준과 측정 — 스트로크 지연

| 항목 | 값 |
|---|---|
| 다음 점까지 잇는 시간 (100만 픽셀 레이어) | **0.20 ms** |
| 다음 점까지 잇는 시간 (**1억** 픽셀 레이어) | **0.19 ms** |
| 칠하는 중 한 프레임 | 4.4 ms |
| 스트로크가 만진 타일 | 2개 |

**두 수치가 같다는 것이 결과다.** 레이어가 100배 커져도 비용이 그대로인 이유는 커버리지를
256픽셀 타일에 담고 **닿은 타일만** 할당하기 때문이다(설계 §2.3). 화면에 보이는 것은 레이어의
원래 버퍼 + 바뀐 타일 패치이고(`LiveEdit`), 레이어 전체를 다시 만드는 일은 스트로크가 끝날 때
한 번뿐이다. 포인터 이동당 총지연은 약 5 ms.

### 5.5 이 과정에서 고친 것

- **C의 `long` 은 윈도우에서 32비트다.** `heal_coverage_bounds` 가 돌려주는 네 값을 C# `long`
  (64비트)으로 읽어 **두 개를 하나로 합쳐 버리고** 있었다. 커널을 실제로 부르는 테스트가 첫
  실행에서 잡았다. `wand_mask` 의 반환값도 같은 문제를 안고 있었다.
- 측정 환경 표기 오류: 러너를 "GPU 없음(WARP)"이라고 적었으나 실제로는
  `Microsoft Basic Render Driver` 이고 `driver` 는 `hardware` 로 보고된다. 어댑터 이름을
  보고서에 남기도록 고치고 문서를 정정했다.

### 5.6 커널 연결 현황

8개 중 6개가 실제로 호출된다: `BrushPixels`·`LevelsPixels`(M0·M2), `WandPixels`·`HealPixels`·
`ContentFill`(M4), `NoisePixels`(바인딩 완료). 남은 `AdjustPixels`·`LensPixels` 는 조정과 렌즈
보정이라 M5 몫이다.

### 5.7 미룬 것

레이어 마스크에 칠하기(마스크를 고르는 UI가 M6에 생긴다), 모든 레이어를 샘플링하는 복제 도장,
스머지·리퀴파이(원본에는 있으나 M4 행에 없다), 색상 선택기와 브러시 설정 UI(M6), 내용 인식
채우기의 메뉴 항목(M6).

## 6. M5 — 조정·필터

**범위**: Levels·Curves·HueSat·Exposure·GradientMap·Grain(조정 레이어와 이미지 메뉴),
가우시안·동작 흐림·노이즈 추가·렌즈 보정(필터 메뉴), 라이브 프리뷰.

### 6.1 핵심 아이디어: 조정은 "화면에 이미 줄어든 프레임"에 건다

조정 레이어는 자기 픽셀이 없다. 그 아래까지 합성된 **프레임을 읽어** 필터를 걸고 되써 넣는다.
그런데 캔버스의 프레임은 M3 덕분에 이미 창 크기다 — 1억 픽셀 문서라도 조정이 만지는 것은
창 한 장이다. 그래서 조정 레이어는 문서 크기와 무관하게 창 크기만큼만 일하고, 설정을 바꾸는
것은 프레임을 다시 그리는 것과 같다. 라이브 프리뷰가 따로 필요 없다.

필터(파괴적 적용)는 레이어 픽셀에 걸리므로 같은 성질을 따로 만들어야 했다. 프리뷰는 레이어를
**렌더러가 어차피 읽을 피라미드 단계에서, 화면에 보이는 부분 + 필터가 닿는 거리만큼만** 잘라
거른다(`FilterPreview`). 원본은 긴 변 2048(조정은 8000)로 줄인 사본을 거르는데, 이러면 맞춤
화면에서는 과하고 확대 화면에서는 흐리다. 잘라 거르는 쪽은 둘 다 창 크기다.

### 6.2 만든 것

| 구성 | 내용 |
|---|---|
| 조정 레이어 | 6종 전부. 불투명도·마스크·폴더 마스크·블렌드 모드·클리핑 그룹 안/밖 |
| 이미지 메뉴 | 같은 6종을 레이어 픽셀에 확정, 선택 영역 안에서만 |
| 필터 메뉴 | 가우시안 흐림(σ 0.1–250), 동작 흐림(1–2000px, ±90°), 노이즈 추가, 렌즈 보정 |
| 확정 | 흐림은 닿는 거리만큼 레이어를 넓혔다가 빈 곳을 다듬는다(원본 순서). 셰이프 기록은 지운다 |
| 프리뷰 | `LiveEdit` 가 "이 픽셀을 이 자리에" 를 말할 수 있게 되어, 잘린 프리뷰가 그대로 합성된다 |
| 디스토트 프리뷰 | M3이 넘긴 것. 드래그 중에도 픽셀이 네 꼭짓점에 들어간 모습을 보여준다(`DistortPreview`) |
| 커널 | 남은 두 파일(`AdjustPixels`·`LensPixels`) 연결. 내보낸 커널 중 `rgba_clamp_premultiplied` 만 호출자가 없다 — 원본은 Lanczos 링잉 뒤처리에 쓰는데, 이 이식에는 링잉하는 필터가 없다(M2에서 박스 필터로 바꿨다) |
| 임시 조작 | Ctrl+L/M/U, F2–F8로 열고 가로 드래그로 주 설정값, Enter 확정·Esc 취소, Shift는 조정 레이어로 |

### 6.3 설계 판단

1. **조정은 Direct2D 효과가 아니라 Core에서 CPU로 돈다.** 설계 표(3절)는 `CIColorCube →
   D2D1LookupTable3D` 를 적어 두었지만, 원본을 다시 읽어 보니 Core Image를 쓰는 조정은
   Hue/Saturation 하나뿐이었다. Levels·Curves·Exposure·GradientMap·Grain은 원본도 C 커널이다.
   그래서 원본 방식 그대로가 CPU이고, 이렇게 하면 두 백엔드가 **같은 코드로 같은 픽셀**을
   낸다 — 백엔드 비교(M2의 자산)가 조정 레이어에도 그대로 선다(최대 4, 평균 0.04 = 정확 비교와
   동일). D2D 효과는 각자 반올림과 프리멀티플 처리가 달라 이 성질을 잃는다.
2. **Hue/Saturation은 원본의 33점 큐브를 그대로 만들고 삼선형으로 조회한다.** `CIColorCube` 가
   하는 일이 그것이다. 조회는 직선 색으로 한 번만 — 원본 주석이 "두 번 나눴더니 반투명 파랑이
   128에서 94가 됐다"고 기록한 함정이다.
3. **조정 레이어의 불투명도·마스크는 "원본과 조정본의 선형 보간"이다.** 원본은 조정본을 원래
   프레임 위에 source-over로 그리는데, 반투명 가장자리에서는 반투명 사본 둘이 겹쳐 두꺼워진다.
   같은 알파끼리의 프리멀티플 보간은 정확하다. 가중치(불투명도 × 모든 마스크)는 계산하지 않고
   **흰 1픽셀을 늘려 그려서** 얻는다 — 회전된 폴더 마스크, 분리된 마스크까지 렌더러가 평소
   샘플링하는 그대로 나온다.
4. **Levels는 원본과 일부러 다르다.** 원본 `LevelsFilter` 는 반투명 픽셀을 언프리멀티플한 뒤
   `levels_apply` 를 부르는데, 커널이 스스로 알파로 나누므로 두 번 나뉘어 밝아진다. Curves와
   Exposure는 원본도 프리멀티플 그대로 넘긴다. 여기서는 셋 다 그렇게 한다.
5. **`levels_apply` 는 픽셀마다 부르지 않고 조회표로 만든다.** 이 커널은 (채널 값, 알파)의
   순수 함수라 채널당 입력이 65,536가지뿐이다. 설정마다 그 전부를 커널에 한 번 통과시켜 답을
   표로 두면 결과는 커널과 **비트 단위로 같고**(테스트가 고정), 창 한 장에 40 ms 걸리던 것이
   1.8 ms가 된다. 커널 파일은 원본 그대로다.
6. **작은 σ의 가우시안은 커널을 그대로 돌린다.** 상자 흐림 3번은 σ와 무관한 비용이 장점이지만
   정수 폭으로는 작은 σ의 분산을 못 맞춘다(σ=1에서 2/3 또는 4/3 — 첫 CI가 잡았다). σ<2는
   진짜 커널, 그 이상은 상자 3번(σ=2에서 분산의 5/6).
7. **디스토트 프리뷰는 D2D 효과가 아니라 확정에 쓰는 리샘플러를 그대로 쓴다.** M3 메모는
   `D2D13DPerspectiveTransform` 을 적어 두었지만, `QuadWarp.Resample` 을 화면 좌표의 꼭짓점과
   창 영역으로 제한해 돌리면 프리뷰가 곧 결과이고 두 백엔드가 같은 픽셀을 그린다. 한 프레임은
   많아야 창 한 장이다. 단, 레이어 자기 마스크는 드래그 중에는 원래 자리에 있다 — 확정하면 새 상자로
   늘어나므로, 마스크가 있는 레이어는 손을 뗄 때 한 번 달라진다.
8. **조정 레이어가 있으면 문서를 먼저 별도 면에 합성한다.** 창 면에는 셸이 먼저 깔아 둔
   책상 회색과 흰 종이가 있고, 조정이 그것까지 물들이면 안 된다.

### 6.4 완료 기준과 측정 — 라이브 프리뷰

"라이브 프리뷰 동작"을 CI가 떨어뜨릴 수 있는 수치로 바꿨다. 프리뷰가 라이브인지는 기계 속도가
아니라 **설정 하나를 바꿀 때 일이 어디로 가는가**로 정해진다. 프레임만큼이면 어떤 문서에서도
따라오고, 레이어만큼이면 큰 문서에서는 어떤 기계도 못 따라온다. 그래서 M3·M4처럼 판정은 픽셀
수로 하고 시간은 옆에 기록만 한다.

1억 픽셀 문서, 1280×800 창, Microsoft Basic Render Driver(= CPU 래스터화):

| 항목 | 값 | 판정 |
|---|---|---|
| 조정 레이어 6장이 프레임당 처리한 픽셀 | 6,144,000 = **창 × 6** | ≤ 창 × 장 수 |
| 필터 프리뷰가 설정 변경마다 거른 픽셀 (맞춤) | 1,562,500 = 창의 1.53배 | ≤ 창 × 4 |
| 필터 프리뷰가 설정 변경마다 거른 픽셀 (100%) | 1,028,966 = 창의 1.00배 | ≤ 창 × 4 |
| 백엔드 차이 (조정 레이어 전종 + 마스크·클리핑·블렌드) | 최대 4, 평균 0.04 | 최대 16, 평균 0.5 |
| 백엔드 차이 (필터 프리뷰·디스토트 프리뷰, 자기 마스크 포함) | 최대 1, 평균 0.013 | 최대 8, 평균 0.2 (정확 비교와 같은 기준) |
| 프레임 시간: 조정 없음 / 6장 / 6장 값 바꾸는 중 | 52 / 133 / 135 ms | 기록만 |
| 필터 프리뷰(σ 20): 열기 / 맞춤 / 100% | 555 / 137 / 77 ms | 기록만 |
| 조정 한 장, 창 한 장 기준 | HueSat 48 · Grain 36 · GradientMap 4.5 · Levels/Curves/Exposure 1.8 ms | 기록만 |

"열기" 555 ms는 1억 픽셀 레이어의 피라미드를 한 번 만드는 비용이고, 그 뒤로는 자른 부분과
필터만 다시 한다.

### 6.5 이 과정에서 고친 것

- **업로드 캐시가 일회용 버퍼로 차고 있었다.** Direct2D 업로드 캐시는 버퍼 참조를 키로 쓰는데,
  클리핑 그룹 합성본처럼 한 번 그리고 버리는 버퍼도 들어가 다시는 맞을 일 없는 항목이 프레임마다
  창 한 장씩 쌓였다(M2부터 있던 문제). `BufferSource.Cacheable = false` 로 표시한다.
- 연속된 조정 레이어는 면을 한 번만 읽고 한 번만 쓴다. 다만 측정해 보니 시간은 읽기·쓰기가
  아니라 조정 연산 자체였다(183 → 173 ms). 실제로 줄인 것은 5번(조회표)이다(→ 133 ms).

### 6.6 미룬 것

- **대화상자와 슬라이더**(레벨 히스토그램, 곡선 편집기, 색상 범위 스펙트럼, 색 선택기)는 M6.
  지금은 명령마다 주 설정값 하나를 드래그로 움직인다.
- **HueSat·Grain이 창 한 장에 40–50 ms**. 실제 GPU가 있는 기계에서는 이 둘을 D2D 효과
  (`LookupTable3D`, 픽셀 셰이더)로 옮길 여지가 있지만, 그러면 두 백엔드 비교가 깨지므로 측정이
  요구할 때 한다.
- **동작 흐림 확정은 긴 거리에서 느리다**(픽셀당 거리만큼 표본). 프리뷰는 줄어든 픽셀이라
  괜찮다. 원본은 GPU(`CIMotionBlur`)였다.
- 노이즈 프리뷰는 잘린 영역 기준이라 화면을 옮기면 무늬가 따라 움직인다(확정 결과와는 100%
  배율·화면 안에서만 같다). 원본 프리뷰도 축소본이라 확정과 무늬가 다르다.
- 배경 제거는 M7(AI). 원본에 따로 있는 "가장자리 다듬기" 명령은 없고, 배경 제거 대화상자의 고급 옵션이다(8절).
- **자동 레벨과 캔버스 샘플링은 M6로 넘긴다.** 원본의 `LevelsAutomatic.swift`(히스토그램으로 검정·흰
  점 찾기, 스포이드로 기준 찍기)와 Hue/Saturation의 캔버스에서 색 범위 고르기·드래그 조정이다.
  계산은 Core 몫이지만 전부 대화상자의 버튼·스포이드에서만 불리므로 대화상자와 함께 만든다.
  히스토그램 커널(`levels_histogram`)은 M0부터 연결돼 있다.

## 7. M6 — UI 완성과 다국어

**목표**: 원본의 전 기능을 윈도우 UI로 쓸 수 있게 하고, **언어 설정으로 영어/한국어를 고르며,
한국어로 두면 모든 표기가 한국어**가 되게 한다.

원본 메뉴를 다시 훑어보니 M6는 UI만이 아니다. 메뉴에 있는 명령 상당수가 Core에 아직 없다 —
레이어 병합·그룹·뒤집기, 캔버스·이미지 크기, 선택 영역 반전·확장·축소, 클립보드, 채우기, 새 캔버스,
저장·내보내기. 그래서 단계를 나누고, 단계마다 CI가 떨어뜨릴 수 있는 기준을 둔다.

| 단계 | 내용 | CI 완료 기준 |
|---|---|---|
| ✅ **M6.1** 다국어 기반 | 문자열 표(영/한), 언어 설정 저장, 기존 하드코딩 문자열 이전 | 모든 키가 두 언어에 다 있음. 표 밖 소스에 한글·UI 문자열 리터럴 0개 |
| ✅ **M6.2** 메뉴와 명령 | 네이티브 메뉴 바, 명령 표(이름·단축키·활성 조건) 하나로 메뉴·단축키·히스토리 이름을 만듦, 보기 > 언어 | 자체검사가 두 언어로 메뉴를 만들어 모든 항목이 번역됐는지, 모든 명령이 예외 없이 도는지 확인 |
| ✅ **M6.3** 문서 명령 | 위에 적은 Core 명령들 | Core 테스트 |
| ✅ **M6.4** 패널과 위젯 | D2D 자체 위젯, 레이어 패널, 도구 옵션 막대, 색, 투명 격자 (변형 수치 입력은 M6.5로) | 자체검사가 숨은 창에 UI를 두 언어로 그려 PNG로 남김 + 표시 문자열 전수 번역 검사 |
| ✅ **M6.5** 대화상자 | 새 캔버스·캔버스/이미지 크기·레벨(히스토그램·자동·스포이드)·곡선·색조/채도·필터·JPEG·색 선택·변형 수치 | 같은 방식, F2–F8 임시 단축키 제거 |
| ✅ **M6.6** 탭과 파일 | 여러 문서 탭, 저장 안 한 변경 확인, 끌어다 놓기 | 같은 방식 + 저장·열기 왕복 |

설계 판단 두 가지를 먼저 정해 둔다.

- **`.resx` 대신 코드 안의 문자열 표.** 설계 6절은 `.resx` 를 적었지만, `.resx` 의 언어별 리소스는
  위성 어셈블리(언어마다 DLL)로 나가서 단일 exe 원칙과 부딪친다. 두 언어뿐이고, 표를 코드로 두면
  "키가 빠졌다"가 컴파일·테스트 단계에서 바로 잡힌다.
- **언어는 실행 중에 바꾼다.** 설정에서 고르면 메뉴·패널·대화상자가 다시 그려지고, 선택은
  `%APPDATA%\Compositor_korean_win\settings.json` 에 남는다. 처음 실행은 윈도우 표시 언어를 따른다
  (한국어 윈도우면 한국어, 아니면 영어).

### 7.1 지금까지 (M6.1–M6.2)

- **문자열 표**: `Core/Localization/TextTable.cs` 한 파일에 영/한이 한 줄씩. 테스트가 키 누락,
  빈 문구, 한글 없는 한국어, 한글 섞인 영어, 자리표시자 불일치, **표 밖 소스의 한글**을 막는다.
- **히스토리 이름은 키로 저장**한다. 언어를 바꾸면 실행 취소 목록도 그 언어로 읽힌다.
- **메뉴 바**: 네이티브 Win32 메뉴. 명령 표 하나(`AppCommands`)가 메뉴·단축키·활성 여부·실행 취소
  이름을 모두 만든다. 언어는 편집 › 환경 설정 › 언어. 바꾸는 즉시 메뉴·제목이 다시 만들어진다.
- **파일**: 열기(.comp·이미지)·저장·다른 이름으로 저장·PNG로 내보내기. 대화상자는 윈도우 공용
  대화상자라 틀은 윈도우 언어를 따르고, 파일 형식 이름과 오류 문구는 고른 언어를 따른다.
- **Esc가 더 이상 프로그램을 끄지 않는다.** 파일 › 끝내기(Ctrl+Q). M5의 F2–F8 임시 키는 메뉴로 대체.
- **자체검사**: 메뉴를 윈도우에서 두 언어로 읽어 90항목 전부 확인(번역 누락 0), 비대화형 명령 25개를
  두 번씩 실행, 한국어 실행 취소 이름 확인("렌즈 교정").

이 과정에서 고친 것:

- **히스토리가 버린 단계의 픽셀을 해제하지 않았다.** 한도를 넘어 오래된 단계를 버려도 비관리 메모리는
  그대로라, 1억 픽셀 레이어에 획 하나마다 400MB가 영영 남았다. 캔버스의 히스토리는 이제 픽셀을
  소유하고(`ownsPixels`), 버린 단계의 버퍼 중 현재 문서와 남은 단계 어디서도 닿지 않는 것만 해제한다.
  문서를 닫거나 새로 열면 나머지도 해제한다. 자체검사의 "누수 0" 이 이를 확인한다.
- **스왑체인을 창마다 새로 만든다.** 첫 창의 체인을 다른 창에 재사용하면 Direct2D가 접근 거부로 실패했다.

### 7.2 M6.3 — 문서 명령

원본 메뉴의 명령 중 대화상자가 필요 없는 것은 전부 들어갔다. 각 명령은 Core의 순수 함수
(문서 → 다음 문서, 해당 없으면 null)이고 셸은 히스토리 한 단계로 감싸기만 한다.

| 메뉴 | 명령 |
|---|---|
| 파일 | 열기·이미지 가져오기·닫기·저장·다른 이름으로 저장·PNG/JPEG로 내보내기·끝내기 (저장 안 한 변경 확인) |
| 편집 | 실행 취소·다시 실행·잘라내기·복사·병합하여 복사·붙여넣기·전경색/배경색으로 칠하기·지우기·내용 인식 채우기 |
| 이미지 | 조정 6종 + 색상 반전, 캔버스 가로/세로 뒤집기 |
| 레이어 | 새 레이어·복제(선택 영역이면 복사한 레이어)·잘라낸 레이어·삭제·레이어 마스크(추가·사용 안 함·삭제)·새 조정 레이어·클리핑 마스크·그룹화·그룹에서 꺼내기·표시/숨기기·앞으로/뒤로·병합·가로/세로 뒤집기 |
| 선택 | 모두·해제·반전·레이어 픽셀·확장·축소 |

Core에만 있고 대화상자를 기다리는 것: 새 캔버스(`DocumentCommands.New`), 캔버스 크기(`ResizeCanvas`,
기준점 9방향), 이미지 크기(`ResizeImage`, 레이어마다 새 상자로 다시 샘플링 — 원본 `ImageResizer` 와
같고, 자유 변형과 같은 리샘플러라 회전된 레이어의 비균일 배율도 받는다). 이름 바꾸기는 레이어 패널(M6.4).

설계 판단:

- **선택 확장·축소는 정확한 유클리드 거리 변환**(Felzenszwalb)으로 한다. 모서리가 둥글게 커지는 것이
  포토샵과 같고, 축소할 때 캔버스 가장자리는 선택 해제로 치지 않는다(포토샵 기본값).
- **클립보드는 PNG + DIB 두 형식**으로 올린다. PNG가 투명도를 지키고(브라우저·오피스·포토샵이 읽음),
  DIB는 그 밖의 모든 프로그램용이다. 붙여넣기는 PNG를 먼저 본다. 원본처럼 복사한 자리에 붙이되,
  클립보드엔 위치를 둘 곳이 없어 시퀀스 번호로 "그 뒤 다른 복사가 없었는지"를 확인한다.
- **Delete 키는 명령 둘에 걸린다** — 선택 영역이 있으면 지우기, 없으면 레이어 삭제. 단축키 하나에
  명령이 여럿이면 실행 가능한 첫 명령이 받는다.

이 과정에서 고친 것:

- **1픽셀 "전체 표시" 마스크가 레이어 가운데서 90%로 옅어졌다.** 소프트웨어 백엔드가 마스크 가장자리
  바깥을 투명으로 샘플링했다. 마스크는 대상 전체를 덮으므로 가장자리 픽셀이 바깥을 대신한다
  (Direct2D 백엔드는 이미 그랬다). 새로 만든 "전체 표시" 마스크(`LayerMask.Solid`)는 알파가 0이라
  아무것도 안 보이게 하던 문제도 함께 고쳤다.
- 자체검사: 메뉴 158항목(두 언어) 번역 누락 0, 명령 55개 실행, JPEG 내보내기 왕복, 클립보드 왕복.

### 7.3 M6.4 — 패널과 위젯

창이 캔버스 하나에서 포토샵식 배치로 바뀌었다 — 위에 도구 옵션 막대, 왼쪽에 도구 줄과 전경/배경색,
오른쪽에 레이어 패널, 아래에 상태 표시줄. 문서가 없으면 가운데에 "열기" 안내가 뜬다.

| 부분 | 내용 |
|---|---|
| 도구 옵션 막대 | 도구마다 다른 설정(크기·경도·불투명도, 셰이프 종류·모퉁이 반경, 그라디언트 종류 등) |
| 도구 줄 | 도구 아이콘(벡터로 그림), 툴팁, 전경/배경색 견본 — 클릭하면 윈도우 색 선택, X 로 교환, D 로 흑백 |
| 레이어 패널 | 혼합 모드(팝업), 불투명도, 행마다 눈·펼침·클리핑 고리·썸네일·마스크 썸네일·이름, Ctrl/Shift 다중 선택, 더블클릭 이름 바꾸기, 휠 스크롤 |
| 패널 아래 버튼 | 조정 레이어(팝업)·마스크·그룹·새 레이어·삭제 — 메뉴와 같은 명령 표를 부른다 |
| 상태 표시줄 | 배율, 캔버스 크기, 문서 이름 |

설계 판단:

- **즉시 모드(immediate mode) 위젯.** 매 프레임 패널을 처음부터 그리면서 클릭 영역을 같이 적는다.
  위젯 객체 트리가 없으니 "문서가 바뀌었는데 패널이 옛 상태"인 경우가 생길 수 없고, 언어를 바꾸면
  다음 프레임이 그대로 새 언어다.
- **글자는 DirectWrite, 글꼴은 언어에 맞춘다** — 한국어는 맑은 고딕, 영어는 Segoe UI.
- **이름 바꾸기만 네이티브 EDIT 상자.** 한글 입력(IME 조합)을 직접 구현하는 것은 이 단계의 몫이
  아니고, 윈도우 입력 상자가 이미 완벽하게 한다.
- **선택 영역 외곽선은 움직이지 않는다.** 원본은 점선이 흐르지만, 어두운 선 위에 밝은 선을 겹친
  정지 외곽선이 같은 정보를 주고 타이머가 필요 없다(M3에서 정한 것 그대로 둔다).

CI 검사(`UiCheck`): 패널이 그리는 모든 문자열과 툴팁을 그릴 때 기록한다. 자체검사가 숨은 창에
마스크·그룹·조정 레이어가 든 문서를 열고 **두 언어 × 모든 도구**로 한 프레임씩 그린 뒤,
한국어일 때 한글이 없거나 영어일 때 한글이 있는 문자열을 잡는다(숫자만 있는 문자열은 통과).
결과: 문자열 1,048개, 번역 누락 0. 화면은 `ui-en.png`·`ui-ko.png`·`ui-*-empty.png` 로
CI 아티팩트에 남아 윈도우 없이도 확인할 수 있다.

레이어 이름("Layer 1", "Group 1")은 **문서 데이터**라 검사 대상이 아니다. 새로 만드는 레이어는
그때의 언어로 이름이 붙고("레이어 1"), 이미 있는 이름은 언어를 바꿔도 그대로다 — 포토샵과 같다.

이 과정에서 고친 것:

- DirectWrite 팩터리는 dwrite.dll 에서 직접 만들고, 글꼴 서식·레이아웃도 팩터리의 가상 함수 표로
  직접 부른다. 처음엔 Vortice 래퍼가 널 참조로 죽는 줄 알고 바꿨는데, 실제 원인은 아래 해제 문제였을
  가능성이 크다. 직접 호출도 잘 돌아서 그대로 둔다.
- **해제된 패널이 다시 그려지며 죽었다.** 자체검사는 창을 닫기 전에 언어를 원래대로 돌리는데, 창이
  닫히는 도중 한 번 더 그려지면서 이미 해제된 팩터리로 새 언어의 서식을 만들려 했다. 해제된 패널은
  이제 아무것도 그리지 않는다.
- 슬라이더 손잡이가 끝까지 가면 오른쪽 값 글자를 덮던 것을 고쳤다.

### 7.4 M6.5 — 대화상자

M5의 "명령마다 설정값 하나를 드래그" 임시 UI가 없어지고, 원본의 시트(sheet)들이 들어왔다. 모두 패널과
같은 자체 위젯으로 그리는 **떠 있는 패널**이고, 열려 있는 동안 나머지 창(패널·메뉴·캔버스)은 멈춘다.
캔버스는 스포이드를 켠 시트에만 클릭을 넘긴다.

| 시트 | 내용 |
|---|---|
| 필터 4종 | 가우시안 흐림(반경), 동작 흐림(각도·거리), 노이즈 추가(양·균일/가우시안·단색), 렌즈 교정(왜곡 제거) |
| 노출·그레인 | 노출·오프셋·감마 / 양·크기·거칠기 |
| 레벨 | 채널, 히스토그램과 입력 검정·감마·흰색 손잡이, 출력 범위, 스포이드 3종, 자동 3종 |
| 곡선 | 채널, 격자 위 곡선, 클릭으로 점 추가·끌어서 이동, 선택한 점의 입력/출력 값, 점 삭제, 곡선 재설정 |
| 색조/채도 | 색상 범위(마스터·6계열), 색조·채도·밝기, 스펙트럼 두 줄과 범위 손잡이, 샘플/추가/빼기 스포이드, 대상 조정(이미지 위를 끌어 채도, Ctrl로 색조), 범위 반전, 색상화 |
| 그라디언트 맵 | 그라디언트, 어두운/밝은 영역 색(색 선택기), 반전 |
| 색 선택기 | 채도·밝기 면, 색조 띠, 새/현재 색, R·G·B·16진수 입력, 캔버스에서 추출 |
| 새 캔버스 | 너비·높이, 크기 한도 안내 |
| 캔버스 크기 | 픽셀/퍼센트, 절대/상대치, 비율 고정, 기준점 9방향, 확장 색상(투명·전경색·배경색·흰색·검정) |
| 이미지 크기 | 픽셀/퍼센트, 비율 고정, 해상도, 리샘플링 끄면 해상도만 변경 |
| JPEG로 내보내기 | 인코딩한 결과를 다시 풀어 보여 주는 미리 보기, 품질, 투명 영역 배경색, 파일 크기 |

공통: 모든 슬라이더 옆에 **숫자 입력칸**이 있고, Enter는 확인, Esc는 입력 중이면 입력 취소·아니면
시트 취소, Tab은 다음 칸이다. 조정·필터 시트에는 미리 보기와 재설정이 있다. 조정 레이어는 레이어 패널에서
**썸네일을 더블클릭**하면 설정 시트가 다시 열린다(이름을 더블클릭하면 이름 바꾸기 — 포토샵과 같다).
이동 도구의 옵션 막대는 X·Y·W·H(비율 고정)·비율·각도를 직접 입력하고 가로/세로 뒤집기를 누를 수 있다.

설계 판단:

- **숫자 입력칸은 네이티브 EDIT 대신 자체 구현.** 시트에 들어가는 것은 숫자(와 16진수 색 코드)뿐이라
  입력기가 필요 없고, 자체 위젯이면 자체검사가 화면의 모든 글자를 읽는다. 한글이 들어가는 레이어 이름만
  네이티브 입력 상자로 남는다(M6.4).
- **윈도우 색 대화상자를 버렸다.** 그 대화상자는 고른 언어가 아니라 윈도우 언어로 나오고, 캔버스에서 색을
  추출할 수 없다. 파일 대화상자는 그대로 윈도우 것을 쓴다(파일 탐색기를 다시 만드는 것은 득보다 실이 크다).
- **시트는 편집 상태를 갖지 않는다.** 열린 필터의 설정은 캔버스가 쥐고 시트는 읽고 쓰기만 한다 —
  슬라이더든 숫자 입력이든 스포이드든, 무엇이 설정을 바꿔도 미리 보기가 같은 길로 따라간다.
- **레벨 히스토그램**은 레이어에 적용할 때는 레이어 자체 픽셀, 조정 레이어일 때는 **그 아래 레이어들의
  합성**을 잰다. 조정 레이어가 실제로 바꾸는 것이 그것이기 때문이다.
- **캔버스 확장 색**은 원본처럼 맨 아래 "캔버스 확장" 레이어로 들어간다. 기존 레이어는 건드리지 않는다.
- **JPEG 품질**은 WIC 인코더 옵션(`ImageQuality`)을 `IPropertyBag2::Write`로 직접 쓴다. 래퍼에 타입 있는
  호출이 없어서다. 다음 내보내기는 마지막 품질에서 시작한다(원본과 같음).
- 시트가 열려 있으면 **메뉴가 회색으로 막힌다**. 대화상자 아래의 메뉴가 도는 일이 없게 한다.

Core에 새로 들어간 것(테스트 포함): `LevelsAutomatic`(자동 레벨 3종·스포이드·히스토그램 표시 배율 —
원본 `LevelsAutomatic.swift`), `HueSampling`(색상 범위 넓히기/좁히기/손잡이 이동/대상 범위 찾기,
결과 스펙트럼, HSB 변환), `LayerTransform.UnitAt`, 캔버스 크기의 확장 색 레이어. M5가 미뤘던 자동 레벨과
캔버스 샘플링이 이것으로 끝났다.

자체검사: 필터·조정 10종, 조정 레이어 편집, 색 선택기, 새 캔버스·캔버스 크기·이미지 크기·JPEG 시트를
**두 언어로 모두 열어** 시트가 뜨는지와 모든 글자를 확인한다 — 문자열 2,666개, 번역 누락 0. 스크린샷은
`ui-ko-*.png`(시트마다)로 아티팩트에 남는다.

원본과 다르게 남긴 것:

- 레벨 히스토그램이 선택 영역으로 가중되지 않는다(레이어 전체를 잰다).
- 새 캔버스가 클립보드 이미지 크기를 제안하지 않고, 시트 안에 "프로젝트 열기/이미지 가져오기" 버튼이 없다
  (파일 메뉴에 있다).
- 이미지 크기에 인치·센티미터 단위와 샘플링 방식 선택이 없다. 변형 입력에 샘플링 선택·자동 선택·
  컨트롤 표시 토글이 없다.
- JPEG 미리 보기는 슬라이더를 놓았을 때 한 번 인코딩한다(원본은 비동기로 계속 갱신).

### 7.5 M6.6 — 탭과 파일

- **여러 문서 탭.** 캔버스 위에 문서마다 탭이 생기고, 탭마다 **자기 문서·실행 취소 기록·파일 경로·확대/위치·
  선택 영역·선택한 레이어**를 따로 가진다. 도구와 그 설정, 전경/배경색은 창의 것이라 탭을 옮겨도 그대로다
  (포토샵과 같다). 열기와 새로 만들기는 이제 현재 문서를 바꾸지 않고 새 탭을 연다. 탭에는 저장하지 않은
  변경이 있으면 `*`가 붙고, 닫기 단추는 먼저 저장 여부를 묻는다. Ctrl+Tab / Ctrl+Shift+Tab(보기 › 다음/이전
  문서)으로 옮겨 다닌다.
- **저장 안 한 변경 확인.** 창을 닫거나 끝내기를 하면 변경된 문서를 하나씩 앞으로 가져와 차례로 묻는다.
  하나라도 취소하면 닫지 않는다.
- **끌어다 놓기.** 탐색기에서 끌어 온 파일은 원본 `ImageFileDrop` 방식대로 들어간다 — `.comp` 프로젝트는
  새 탭으로 열리고, 이미지는 열린 문서의 레이어로 추가되며, 열린 문서가 없으면 첫 이미지가 새 문서가 되고
  나머지가 그 위에 레이어로 들어간다. 시트가 열려 있는 동안에는 받지 않는다.

설계 판단:

- **캔버스는 여전히 필드 하나에 문서 하나를 놓고 일한다.** 탭은 다른 문서가 캔버스를 쓰는 동안 그 필드들이
  기다리는 곳이다. 전환은 지금 문서의 필드를 탭에 넣고 다른 탭의 것을 꺼내는 일이라, 캔버스의 나머지 코드는
  문서가 여럿이라는 것을 몰라도 된다.
- **반쯤 된 일이 있으면 전환하지 않는다** — 붓질 중, 끌기 중, 필터가 열린 동안. 각각이 시작한 문서의
  픽셀이나 기록 단계를 쥐고 있기 때문이다.

자체검사(`FilesCheck`): 마스크·폴더·조정 레이어가 든 문서를 파일 메뉴와 같은 코드로 저장하고 다시 열어,
레이어 이름·종류·배치·조정값·마스크를 비교하고 **모든 픽셀**을 비교한다(최대 차이 0). 이어서 두 탭이 서로의
문서와 기록을 건드리지 않는지, 다음 문서 명령, 이미지·프로젝트 끌어다 놓기, 탭 닫기와 이웃 탭 표시,
빈 창에 이미지 놓기까지 확인한다.

### 7.6 M6 결과

- 원본의 메뉴·패널·시트 대부분이 윈도우 UI로 들어왔다(10절 마무리 검토에서 찾은 차이는 이후 보완했다 — 이 문장은 처음에 "모두"라고 적었으나 사실이 아니었다). 언어는 편집 › 환경 설정 › 언어에서 고르고,
  바꾸는 즉시 메뉴·패널·시트·실행 취소 이름까지 그 언어로 다시 그려진다.
- CI가 매번 두 언어로 메뉴 186항목과 화면 문자열 4,347개를 읽어 **번역 누락 0**을 확인하고, AI 포함판에서
  명령 65개를 실행해 보며, 시트마다 스크린샷을 남긴다(10.1의 후속 보완까지 반영한 수치).
- 윈도우 언어를 따르는 것은 파일 열기/저장 대화상자의 틀과 메시지 상자의 단추(예/아니요)뿐이다. 그 안에
  이 프로그램이 넣는 글(파일 형식 이름, 질문, 오류)은 고른 언어를 따른다.

### 7.7 M6 보완 — M4가 넘긴 것

M6를 마치고 앞 단계의 "미룬 것"(4.6, 5.7, 6.6)을 코드와 대조해 보니 셋이 남아 있었다.

- **레이어 마스크에 칠하기.** 레이어 패널에서 마스크 썸네일을 누르면 마스크가 도구의 대상이 된다(원본
  `isMaskSelected`). 대상인 썸네일에 테두리가 생기고 옵션 막대에 "마스크"가 뜬다.
  - 브러시·그라디언트는 흰색/검정으로 칠하고, 지우개는 반대 색을 칠한다.
  - 흐림 효과는 마스크를 흐리게 한다. 복제 도장·스팟 힐링·문지르기·픽셀 유동화는 마스크에서 아무것도 하지 않는다(원본 규칙).
  - 채우기·지우기(Delete)·반전("마스크 반전")은 마스크에 작동하고, 선택 영역 없이 Delete를 누르면 마스크를 지운다.
  - 전경/배경 색상 칸은 마스크의 검정/흰색을 보여 준다. 누르거나 X를 누르면 둘이 바뀐다.
  - 필터는 꺼진다.
  - 레이어 마스크 추가 직후에는 마스크가 바로 대상이 된다.
  - 선택 › **마스크의 검은 영역**이 마스크가 가리는 부분을 선택 영역으로 불러온다.
- **문지르기·픽셀 유동화.** 흐림 효과 도구의 유형으로 들어갔다(원본 `BlurToolMode`). 옵션은 경도와 강도다.
- **복제 도장의 "모든 레이어 샘플링".** 스트로크를 시작할 때 보이는 문서 전체를 한 번 합성해 거기서 복사한다.

설계 판단:

- **마스크는 레이어의 칠하기 경로를 그대로 쓴다.** 마스크는 RGB가 회색이고 알파가 가득 찬 버퍼라,
  불투명한 회색을 칠하면 알파는 그대로다. 그래서 새 붓을 만들지 않고 칠할 격자와 색만 바꿨다.
  마스크를 따로 옮긴 경우(배치가 있는 마스크)는 그 배치의 격자에서 칠한다.
  한 픽셀짜리 새 마스크는 처음 칠할 때 실제 격자로 펼친다.
- **스트로크 중 마스크 표시.** 칠하는 동안 문서에는 마스크 사본이 들어가고, 붓이 바뀐 타일만 그 사본에 복사한다.
  붓은 원래 마스크에서 칠하므로 불투명도가 "스트로크 전체의 상한"이라는 성질이 그대로 유지된다.
  같은 버퍼를 고쳐 쓰면 겹친 곳이 겹칠 때마다 짙어진다.
- **문지르기·픽셀 유동화는 레이어 자기 격자에서 돈다.** 원본은 문서 크기로 작업한 뒤 결과를 붓 경로를 따라 레이어에 다시 칠한다.
  여기서는 다른 도구와 같이 레이어 픽셀에서 바로 작업하므로 들어가고 나올 때 리샘플링이 없다.
  라이브 표시는 일반 버퍼가 아니라 패치 없는 래스터로 넘긴다. 렌더러가 일반 버퍼의 축소본을 버퍼 단위로
  캐시하는데, 이 버퍼는 스트로크 중에 계속 바뀌기 때문이다.

자체검사(`ToolsCheck`, 18항목): 캔버스에 실제 포인터 입력을 넣어 확인한다.
- 마스크 추가 → 대상이 됨, 색상 칸 표시.
- 브러시가 마스크만 검게 칠하고 레이어 픽셀은 그대로임, 실행 취소 한 번으로 되돌아옴.
- 지우기, 마스크 반전, 검은 영역 선택, 마스크 위 그라디언트.
- 마스크를 대상으로 하는 동안 필터가 꺼짐, 레이어를 누르면 대상이 레이어로 돌아옴.
- 문지르기·픽셀 유동화가 레이어를 바꾸고 기록을 한 단계 남김.

UiCheck는 흐림 효과의 세 유형과 마스크 대상 상태의 옵션 막대까지 두 언어로 읽는다(`ui-ko-mask.png`).

남긴 것(아래 7.8에서 마무리): 마스크를 대상으로 한 복사/잘라내기, 마스크 연결 끊기, 연결이 끊긴 마스크만 따로
변형하기, 마스크 썸네일을 끌어 다른 레이어로 복사하기.

### 7.8 M6 보완 — 마스크 연결·따로 변형·복사

- **연결/연결 해제.** 레이어 행의 두 썸네일 사이에 원본처럼 사슬 단추가 생겼다. 누르면 연결이 끊기고 사슬이
  사라진다. 레이어 › 레이어 마스크 › **레이어 마스크 연결 해제/연결**로도 할 수 있다.
- **레이어를 옮길 때 마스크 처리를 한 규칙으로 통일했다**(원본 `placement(movingLayer:to:)`).
  - 연결된 마스크는 레이어를 따라가고, 연결이 끊긴 마스크는 문서 위 제자리에 남는다.
  - 드래그, 화살표 키, 수치 입력, 여러 레이어 함께 옮기기가 모두 이 규칙 하나를 거친다.
  - 전에는 따로 놓인 마스크를 수치 입력만 데려가고, 드래그와 화살표 키는 두고 갔다. 이번에 함께 고쳤다.
- **연결이 끊긴 마스크를 대상으로 하면** 이동 도구, 화살표 키, 옵션 막대의 X·Y·W·H·비율·각도·뒤집기가 마스크만
  움직인다(원본 `transformTargetsMask`).
  - 옵션 막대에 "마스크"가 표시된다.
  - 기록 이름은 "레이어 마스크 변형"이다.
  - 마스크에는 왜곡(Ctrl+핸들)이 없다.
- **마스크 복사.** 마스크 썸네일을 끌어 다른 레이어의 행에 놓으면, 마스크가 문서 위 같은 자리에 복사된다.
  - 받는 레이어에 마스크가 있었으면 바뀌고, 복사된 마스크가 대상이 된다(원본 `copyMask`).
  - 끄는 동안 놓일 행에 테두리가 표시된다. 제자리에서 떼면 전처럼 마스크를 대상으로 고르는 클릭이다.
- **복사·잘라내기·선택 영역으로 새 레이어(Ctrl+J)** 는 마스크가 대상일 때 마스크의 회색을 가져간다.
  잘라낸 자리는 마스크의 배경색으로 칠한다.
- **따로 놓인 마스크의 바깥.** 마스크 상자 밖은 가장자리의 흰색/검정 중 많은 쪽을 따른다(원본 `background(of:)`).
  그래서 "모두 보이기" 마스크는 절반을 밖으로 옮겨도 나머지를 계속 보인다. 폴더 마스크는 지금처럼 바깥을 가린다.
  - 두 백엔드 모두 반영했다. Direct2D는 바깥 값으로 먼저 채운 뒤 마스크를 덮어쓴다(Copy). 겹쳐 그리면 안쪽 회색이 밝아진다.
  - 렌더 검사에 따로 놓인 마스크가 든 레이어를 넣었다. 백엔드 차이는 전과 같다(정확 비교 최대 4).

자체검사(`ToolsCheck`)는 24항목으로 늘었다. 늘어난 항목은 마스크 복사가 회색을 가져가는지, 연결 해제 후 마스크만
옮겨지는지, 레이어를 옮겨도 연결이 끊긴 마스크는 남는지, 다른 레이어로 마스크를 복사하는지다.

- **왜곡(Ctrl+핸들)할 때 마스크도 함께 옮긴다**(원본 `distort(at:transform:corners:)`, `QuadWarp.Distort`).
  전에는 픽셀만 다시 샘플링해서, 레이어 격자를 따르던 마스크가 새로 생긴 똑바른 상자에 늘어나 얹혔다.
  - 레이어 격자를 따르는 연결된 마스크는 같은 모서리로 같은 상자에 다시 샘플링한다.
  - 따로 놓인 연결된 마스크는 레이어와 같은 원근을 자기 상자에 받는다. 둘레는 가장자리 색이다.
  - 연결이 끊긴 마스크는 제자리에 남고, 한 픽셀짜리 마스크는 그대로 통과한다.
  - 드래그 중 미리 보기에서도 레이어 격자를 따르는 마스크가 픽셀과 함께 휜다(`LiveEdit.Mask`).
    따로 놓인 마스크는 놓을 때 옮겨진다.
  - 원본에서 왜곡은 Ctrl+핸들로 시작하는데, 자체검사는 실제 Ctrl 키 상태를 만들 수 없다. 그래서 Core 테스트
    4개(격자 공유·따로 놓임·연결 해제·한 픽셀)로 확인한다.

## 8. M7 — AI 배경 제거

**목표**: 원본의 필터 › 배경 제거를 윈도우로 옮긴다. 원본은 피사체 인식을 macOS Vision에 맡기므로
그 부분만 ONNX 모델로 바꾸고, 나머지(마스크로 가리기, 다듬기)는 원본대로 만든다.

### 8.1 정한 것

- **모델: BiRefNet-lite fp16**([onnx-community/BiRefNet_lite-ONNX](https://huggingface.co/onnx-community/BiRefNet_lite-ONNX),
  114.5 MB, MIT). 설계 문서가 적어 둔 RMBG-1.4는 비상업용 라이선스라, 이 앱으로 의뢰 작업을 하는 사용자에게
  위반이 되므로 쓰지 않았다. BiRefNet은 공개 비교에서 RMBG-1.4보다 세부(머리카락)가 낫다.
  - 입력 `input_image` float32 [1,3,1024,1024](ImageNet 정규화), 출력 `output_image` [1,1,1024,1024] 로짓.
  - fp16 모델이지만 입출력은 float32라 CPU에서도 그대로 돈다(CI에서 확인).
- **실행: ONNX Runtime 1.24.4 + DirectML 1.15.4.** DirectML을 먼저 시도하고, 세션을 만들지 못하면 CPU로 넘어간다.
  CI 러너는 `Specified display adapter handle is invalid` 로 DirectML이 거절되어 CPU로 돌았다(실제 GPU에서의 속도는 미확인).
- **배포판 둘**: 한 소스에서 `-p:WithAi=false` 로 나눈다.
  - **AI 포함판**(`Compositor_korean_win-ai`): exe + `onnxruntime.dll`(17.3 MB) + `DirectML.dll`(18.5 MB) +
    `modelsirefnet-lite-fp16.onnx` + `licenses\`. 압축 전 약 150 MB.
  - **미포함판**(`Compositor_korean_win`): exe와 고지 파일뿐. ONNX Runtime을 참조하지 않으므로 없는 DLL을
    부를 일이 없다. 배경 제거는 메뉴에 "배경 제거 (AI 포함판 전용)"으로 회색 표시된다.
  - exe 크기 차이는 0.53 MB(7.85 / 7.32 MB)다. 처음에 "ONNX Runtime이 exe를 3.4→7.7 MB로 키웠다"고 판단했는데,
    3.4 MB는 이 문서에 남아 있던 옛 수치였고 M6 끝의 exe가 이미 7.13 MB였다. 잘못 짚은 것이다.
- **릴리스는 M8.** 지금은 CI가 두 배포판을 아티팩트(보관 14일)로 만드는 데까지다.

### 8.2 만든 것

- 필터 › **배경 제거…**(원본 `removeBackground`). 배경을 지우지 않고 **레이어 마스크로 가린다**. 기존 마스크가 가리던
  곳은 계속 가리고, 선택 영역이 있으면 그 안에서만 바뀐다. 적용 후 새 마스크가 대상이 된다.
- 품질 **기본**(모델 결과 그대로) / **고급**: 다듬기(0–40 px, 레이어를 안내 이미지로 쓰는 guided filter) →
  가장자리 이동(−10–10 px) → 대비(0–100 %). 원본 `SubjectRemoval`·`GuidedMatte` 의 순서와 기본값(12, 25, 0)을 따른다.
- 모델은 **백그라운드 스레드에서 한 번만** 돈다. 시트는 "피사체를 찾는 중…"을 보이고, 끝나면 창을 깨운다.
  슬라이더는 모델을 다시 돌리지 않고 그 답에 계산만 다시 한다.
- 미리 보기는 긴 변 1,400 px에서 다듬고, 적용은 3,072 px에서 다듬어 레이어 크기로 늘린다. 원본은 적용 때
  원래 크기로 다듬지만, 그러면 2,400만 화소 사진에서 작업 평면이 수 GB가 된다.
- 모델 로드는 세션당 한 번이다(CPU에서 약 8초).

### 8.3 자체검사

- `AiCheck`: 흐린 바탕 위 어두운 원판 사진을 합성해 모델에 넣는다. 원판 안 평균 1.00, 밖 0.00 → 통과.
  모델 출력이 시그모이드가 필요한지, 평면 순서가 맞는지를 여기서 잡는다.
- 같은 검사가 캔버스에서 메뉴로 배경 제거를 실행해, 640×480 마스크가 원판 위 흰색/모서리 검정인지, 기록 한 단계가 남는지,
  새 마스크가 대상인지 확인한다. 미포함판에서는 명령이 실행되지 않아야 통과다.
- UiCheck가 두 언어로 시트(고급 옵션 포함)를 읽는다(`ui-ko-removebackground.png`).
- **미포함판도 같은 자체검사를 전부 돈다**(메뉴·패널·파일·도구 모두 통과).
- CI 러너 CPU 추론 시간은 9–56초로 실행마다 크게 달랐다. 기록만 하고 판정에 쓰지 않는다.

### 8.4 남긴 것

- 실제 GPU(DirectML)에서의 동작과 속도 — CI에 GPU가 없다.
- 취소해도 이미 시작한 추론은 끝까지 돈다(ONNX Runtime 실행을 중간에 끊지 않는다). 결과는 버린다.
- 원본 이후의 확장(생성형 채우기, 업스케일)은 설계 7절대로 같은 구조에 얹을 수 있지만 범위 밖이다.

## 9. M8 — 배포

**목표**: 태그를 푸시하면 릴리스가 만들어지고, 사용자는 설치 파일로 설치·제거하며, 앱에서 새 버전을 확인할 수 있다.

### 9.1 만든 것

- **설치 파일(Inno Setup)** — `installer/Compositor_korean_win.iss` 하나로 두 판을 만든다.
  - 사용자별 설치: `%LOCALAPPDATA%\Programs\Compositor_korean_win`, 관리자 권한 없음.
  - 설정 › 앱(프로그램 추가/제거)에 "Compositor 한국어판"으로 등록된다. 제거하면 프로그램 폴더, 설정
    (`%APPDATA%\Compositor_korean_win`, 앱이 쓰는 유일한 다른 곳), 등록 정보가 모두 지워진다.
  - 두 판이 같은 AppId라 한 프로그램으로 취급된다. 미포함판을 AI 포함판 위에 깔면 런타임과 모델을 지운다.
  - 설치 화면은 한국어/영어. 아이콘은 원본 앱 아이콘(MIT)을 `.ico`로 묶어 exe·창·설치 파일에 쓴다.
- **CI가 매번 실제로 설치해 본다**: AI 포함판 설치 → 미포함판으로 교체 → 제거 후 폴더·설정·등록 정보가
  남지 않았는지 확인한다.
- **릴리스**: `v1.2.3` 태그를 푸시하면 버전이 exe에 새겨지고(`-p:Version`), 두 자체검사가 모두 통과했을 때만
  릴리스가 만들어진다. 올라가는 것: 설치 파일 2개, 휴대용 zip 2개, `update.json`, `SHA256SUMS.txt`.
- **업데이트 확인**(도움말 › 업데이트 확인…): 최신 릴리스의 `update.json` 을 읽어 새 버전이면 릴리스 페이지를 연다.
  사용자가 누를 때만 실행되고, 스스로 내려받거나 설치하지 않는다. 원본의 Sparkle `appcast.xml` 자리.
  - 처음엔 HttpClient를 썼는데 exe가 3 MB 커져서 WinINet으로 바꿨다(윈도우 내장, 리다이렉트·프록시 처리).
- **정보** 창에 버전이 나온다.

### 9.2 릴리스 기록

| 버전 | 내용 |
|---|---|
| v1.0.0 | 첫 릴리스 |
| v1.0.1 | GPU(DirectML)에서 배경 제거가 겹쳐 실행되면 두 번째가 실패하던 문제 수정 — 실행을 한 번에 하나로 줄 세운다. `SHA256SUMS.txt` 를 LF 줄바꿈으로(`sha256sum -c` 가 그대로 읽도록) |

v1.0.0을 이 PC(RTX 4060)에 실제로 설치해 자체검사를 돌려서 찾은 것이다. 배경 제거 한 번은 DirectML로 약 2초였지만,
취소한 추론이 아직 도는 동안 새 추론이 시작되자 `DmlCommandRecorder` 오류(80004005)가 났다. CI 러너는 GPU가 없어
CPU로 돌기 때문에 드러나지 않았다.

### 9.3 남긴 것

- **코드 서명 없음.** 브라우저로 받으면 SmartScreen 경고가 뜬다(설계 8절의 미해결 비용). 릴리스 노트에 안내했다.
- 업데이트는 확인만 한다. 자동 설치는 서명이 전제라 하지 않았다.

| 메뉴 | 보기 › 변형 컨트롤 표시(Ctrl+H) | 이동 도구의 변형 테두리와 손잡이를 켜고 끈다 |
| 레이어 패널 | 드래그 이동·Alt 복제 | 위·아래·그룹 안 배치와 Alt 드래그 복제 |
| 레이어 패널 | 우클릭 메뉴·검정 마스크 | 행 메뉴와 모두 가리기 마스크 추가 |
| 레이어 패널 | Ctrl/Shift+썸네일 | 픽셀·마스크 검은 영역을 선택하고 마스크를 켜고 끈다 |

후속 보완을 마친 CI는 Core 테스트 500개와 셸 도구 자체검사 45개를 두 배포판에서 통과했다.
스포이드 자체검사는 앞선 마스크 검사에서 편집 대상이 유지되는 동작을 놓쳐 한 번 실패했다. 마스크가
대상일 때 팔레트를 건드리지 않는 것과 레이어 픽셀로 돌아온 뒤 표시 색을 얻는 것을 나눠 검증해 고쳤다.

### 10.2 일부러 원본과 다르게 둔 것 (이미 각 절에 기록)

- 레벨 히스토그램이 선택 영역으로 가중되지 않는다. 새 캔버스가 클립보드 크기를 제안하지 않는다.
  이미지 크기에 인치·센티미터와 샘플링 선택이 없다. JPEG 미리 보기는 슬라이더를 놓을 때 한 번 인코딩한다(7.4).
- 선택 영역 외곽선은 움직이지 않는다(7.3).
- 배경 제거 적용 시 3,072 px에서 다듬어 늘린다(원본은 원래 크기)(8.2).
- 업데이트는 확인만 하고 설치는 하지 않는다(9.1).

### 10.3 알려진 한계

- 코드 서명이 없어 SmartScreen 경고가 뜬다(9.3).
- 색조/채도·그레인 조정 레이어가 창 한 장에 40–50 ms, 긴 동작 흐림 적용이 느리다(6.6).
- 배경 제거를 취소해도 이미 시작한 추론은 끝까지 돈다(결과는 버림)(8.4).
- 배경 제거의 GPU 동작은 RTX 4060 한 대에서만 확인했다(v1.0.1, 약 2.3초). AMD·Intel GPU는 미확인.

### 11.1 `c521b89`가 CI에서 실패한 이유

고급 입력 묶음의 자체검사가 Shift+Plus로 활성 레이어를 Multiply로 바꾼 뒤 다음 프레임에서
`Direct2DBackend.Surface.Draw`가 `E_INVALIDARG`로 죽었다. 코드 자체는 이 묶음 이전부터 있던 결함이다.

화면 캔버스는 스왑 체인 백버퍼에 직접 그리는데(`CreateWindowSurface`), 백버퍼의 알파 모드는 `Ignore`다.
혼합 모드는 이미 그려진 것을 복사해 배경 입력으로 쓰는데 그 복사본을 늘 `Premultiplied`로 만들었고,
`CopyFromBitmap`은 형식이 다르면 거부한다. 오프스크린 렌더(내보내기·`RenderCheck`)는 대상도
`Premultiplied`라 통과했기 때문에, **Normal이 아닌 레이어가 화면에 보이면 앱이 죽는** 결함이 지금까지
드러나지 않았다. 복사본을 대상의 픽셀 크기·형식 그대로 만들도록 고쳤다(`069305a`).

### 11.3 맥 보조키 → 윈도우 포토샵 기준

원본은 맥 앱이므로 보조키는 **윈도우판 포토샵의 대응**으로 옮긴다: Command → Ctrl, Option → Alt,
맥의 delete 키(Return 위) → Backspace. 메뉴 단축키와 캔버스 조작은 이미 이 규칙이었고, 윈도우에만 있는
동작을 맞췄다(`CI 35941156987`).

| 항목 | 윈도우 포토샵 기준 동작 |
|---|---|
| Alt를 쓴 포인터 조작 뒤 Alt 떼기 | 메뉴 막대가 열리지 않는다. Alt만 눌렀다 떼면 여전히 열린다 |
| Backspace / Delete | 둘 다 지우기(선택 없으면 레이어 삭제). Alt+둘 중 하나 전경색 채우기, Ctrl+ 배경색 채우기 |
| Ctrl+Space / Alt+Space 클릭 | 어느 도구에서든 임시 확대/축소, 가로 드래그는 연속 확대. Alt+Space가 창 시스템 메뉴를 열지 않는다 |
| Alt+P | 대화상자 미리 보기 전환(원본 Option-P) |
| 획·다각형 올가미 진행 중의 키 | 메뉴보다 먼저 받는다. Backspace/Delete는 꼭짓점 취소, 획 도중 Ctrl+Z 무시 |
| 휠 | 확대로 유지한다(원본은 휠=이동, Command/Option+휠=확대). 사용자 결정(2026-09-24) |

### 11.4 감사 뒤에도 원본과 다른 것

- **Shift 드래그 직선**: 원본은 수평·수직 두 방향, 이식판은 45° 포함 여덟 방향이다(`Straightened`, 이전 결정).
- **보조키를 누르고 떼는 순간의 즉시 반영**: 원본은 `flagsChanged`로 마키 정사각형·자르기 대칭을 포인터가
  움직이지 않아도 바로 다시 그린다. 이식판은 다음 포인터 이동 때 반영한다.
- **커서 모양**: 원본은 도구·보조키·손잡이에 따라 커서를 바꾼다(올가미 모드 배지, 변형 손잡이 방향 등).
  이식판 커서 대조는 이번 감사 범위 밖이었다.
- **이번에 조작 단위로 대조하지 않은 것**: 레이어 목록(`NativeLayerList.swift`)의 마우스 조작, 색조/채도의
  캔버스 드래그 조정(`hueTargeting`), 레벨의 캔버스 표본 추출. 10.1에서 기능 단위로는 확인했다.

의도적으로 다르게 두는 10.2와 배포·성능 한계인 10.3은 이 표의 기능 누락과 구분한다.

### 13.2 텍스트

**Core는 글꼴 엔진을 갖지 않는다.** `IGlyphSource`(`Text/GlyphSource.cs`)가 글자마다 윤곽선(직선·3차
베지어)과 전진폭을 넘겨주면, Core가 줄 배치(`TextRendering`), 뒤틀기(`TextWarping`), 채우기
(`OutlineRaster`)를 한다. 셸은 DirectWrite를 연결하고, 테스트는 상자 모양 글리프를 넣는다. 그래서
텍스트 테스트도 다른 Core 테스트처럼 백엔드·디스플레이 없이 돈다.

- **뒤틀기는 채우기 전 윤곽선에 건다.** 채운 픽셀을 휘면 가장자리가 리샘플로 뭉개진다. 윤곽선의 점을
  옮기고 곡선은 잘게 나눠 옮긴 뒤 채우므로, 휜 글자도 가장자리가 깨끗하다. 스타일은 포토샵의 15종(부채꼴,
  아래·위 부채꼴, 아치, 돌출, 아래·위가 넓은 조개, 깃발, 파형, 물고기, 상승, 물고기 눈, 부풀리기,
  양쪽 누르기, 비틀기)이고 구부리기·가로 왜곡·세로 왜곡은 -100~100이다.
- **채우기는 nonzero, 한 행에 16샘플이다.** 한글 글꼴은 획끼리 겹치는 윤곽선이 많다. even-odd로 채우면
  겹친 곳이 구멍으로 뚫린다.
- **레이어는 레시피(`LayerText`)와 평범한 래스터를 함께 가진다.** 원본이 도형 레이어에 `shape` 레시피를 두는
  방식과 같다. 레시피의 `Rendered`가 지금 래스터와 같은 버퍼일 때만 "살아 있는 텍스트"다. 브러시나
  필터로 픽셀을 바꾸면 버퍼가 바뀌므로 저절로 일반 레이어가 되고, 다시 조판해서 칠한 것을 덮는 일이 없다.
  "문자 래스터화" 메뉴는 레시피를 명시적으로 떼어 낸다.
- **기준점은 문서에 고정된다.** 크기·글꼴·뒤틀기를 바꾸면 래스터 크기가 달라지는데, 기준점
  (`AnchorX/Y`)을 문서 좌표에 붙잡아 두고 다시 놓으므로 글자가 제자리에서 커지고 작아진다.

셸(`Text/DirectWriteGlyphs.cs`):

- **DirectWrite를 Vortice 래퍼가 아니라 COM 표(vtable)로 직접 부른다.** 래퍼의 글꼴 호출은 트리밍된
  NativeAOT 빌드에 남지 않는 리플렉션을 쓴다. `Ui`가 이미 `CreateTextFormat`을 이렇게 부르고 있다.
  슬롯 번호는 `dwrite.h` 선언 순서이고, 윤곽선 싱크(`ID2D1SimplifiedGeometrySink`)는 소스 생성기
  (`GeneratedComClass`)로 구현했다.
- **글꼴에 없는 글자는 맑은 고딕 → Segoe UI Symbol → Segoe UI Emoji에서 가져온다.** 라틴 전용
  디스플레이 글꼴로 한글을 쳐도 네모 칸이 나오지 않는다. 윈도우 자체의 대체 순서와 같다.
- 글꼴 목록은 한국어 UI에서 한국어 이름(예: 맑은 고딕)으로 보여 주고, 저장은 영어 이름으로 한다.
  다른 언어의 윈도우에서 열어도 같은 글꼴을 찾기 위해서다.

문자 도구(`CanvasText.cs`, 단축키 T):

- 캔버스를 클릭하면 새 텍스트 레이어를 만들고, 기존 텍스트를 클릭하면 그 레이어를 편집한다. 입력은 포인터
  옆에 뜨는 **네이티브 여러 줄 입력칸**으로 받는다. 한글이 IME를 거쳐야 하는데, 직접 그린 입력칸은 조합
  표시를 다시 구현해야 하기 때문이다.
- 글자를 칠 때마다 레시피로 레이어를 다시 조판한다. **클릭부터 입력칸을 닫을 때까지가 실행 취소 한 번**이다
  ("텍스트 추가"/"텍스트 편집"). Escape는 편집 전으로 되돌리고, 비운 채 닫은 새 레이어는 사라진다(포토샵과 같다).
- 입력 중 만든 중간 래스터는 기록에 들어가지 않으므로 다음 조판이 대체하는 즉시 해제한다. 기록에는
  처음과 마지막만 남는다.
- 옵션 바: 글꼴, 크기, 굵게, 기울임, 정렬 3종, 자간, 행간, 색, 뒤틀기. 옵션 바, 뒤틀기 창, 색 선택기의
  스타일 변경은 창을 한 번 열고 닫는 동안 **한 기록**("텍스트 스타일")으로 묶는다.

### 13.3 레이어 효과

드롭 섀도, 외부 광선, 획(바깥쪽·안쪽·가운데)이다(`Effects/`). 메뉴 "레이어 스타일"로 연다.

- **합성할 때 레이어의 모양에서 그린다.** 레이어 자신의 픽셀 격자에 효과가 닿는 거리만큼 여백을 두고
  계산한 뒤, 레이어의 배치를 여백만큼 키워 문서에 놓는다. 그래서 회전·뒤집기·확대한 레이어도 픽셀과
  똑같이 효과를 달고 다닌다. 크기 값은 문서 픽셀로 받아 레이어 배율로 나눈다.
- **획은 가장자리로부터의 부호 있는 거리의 띠다.** 거리 변환(Felzenszwalb)으로 각 픽셀이 반대편까지 얼마나
  떨어졌는지 구하고, 픽셀 자신의 커버리지로 경계 위치를 보정한다. 그래서 앤티앨리어싱된 글자에 1픽셀 획을
  둘러도 매끄럽다. 그림자·광선의 스프레드는 흐리기 전에 같은 거리만큼 모양을 키운다.
- **버퍼와 설정을 키로 캐시한다(LRU 32개).** 픽셀은 불변이라 모양은 픽셀이 바뀔 때만 바뀐다. 이동·확대만
  하는 프레임은 흐림을 다시 계산하지 않는다. 여백을 붙인 격자가 1억 2천만 픽셀을 넘으면 메모리를
  지키기 위해 효과를 그리지 않는다.

### 13.4 도형 확장

도형 도구에 다각형(변 3~64), 별(꼭짓점 수, 안쪽 깊이 0.05~0.95, 곡선), 선(두께), 칠 켜고 끄기,
외곽선(두께·색)을 더했다(`Tools/ShapeTool.cs`). 곡선 별은 꼭짓점 사이 변을 안쪽 모서리를 조절점으로 한
2차 베지어로 만든다. 포스터 디자인의 4각 반짝이 별이 이것이다.
칠은 전경색, 외곽선은 배경색으로 그린다. 옵션 바에 외곽선 색을 따로 고르는 칸은 없다.

### 13.5 저장 형식 호환

- 텍스트 레시피는 `text`, 효과는 `effects` 키에 저장한다. 둘 다 이 포트에만 있는 키이고 macOS판은
  모르는 키를 무시한다. 텍스트 레시피는 **래스터가 그 레시피로 그린 것일 때만** 쓴다. 그래서 macOS판이
  보여 주는 픽셀과 이 포트가 아는 텍스트가 어긋나지 않는다.
- 검증 규칙도 옮겼다: 범위를 벗어난 값은 거부하고, 그룹·조정 레이어·이미지 없는 레이어는 텍스트를
  가질 수 없다.
- **새 도형은 `shape` 레시피로 저장하지 않는다.** macOS판의 `ShapeKind`는 `Rectangle`·`Ellipse` 둘뿐이라,
  `Star` 같은 값을 쓰면 macOS판이 파일을 못 읽는다. 지금 도형 도구는 도형을 레이어 픽셀로 그리고
  `shape` 레시피를 남기지 않는다(`ShapeSettings.ToStyle()`을 부르는 곳이 없다). 나중에 도형 레이어를
  다시 그릴 수 있게 레시피를 남긴다면, 원본에 없는 종류는 따로 이 포트 전용 키에 둬야 한다.

**포토샵에서는 열리지 않는다.** `.comp`는 원본 Compositor 전용 형식이다. 이 포트가 쓰는 파일은
`manifest.json`과 레이어별 PNG를 담은 zip이고(macOS판은 같은 내용을 폴더 패키지로 쓴다), 포토샵은 이
형식을 모른다. 압축을 풀면 `images/` 안의 PNG를 하나씩 열 수는 있다. 하지만 위치·크기·회전·불투명도·혼합
모드·마스크·그룹은 `manifest.json`에만 있어서, 풀어 연 PNG로는 원래 구성이 나오지 않는다. 포토샵으로
넘기는 방법은 지금 **PNG/JPEG 내보내기(한 장으로 합쳐짐)** 뿐이다. 합성기를 거치므로 텍스트·효과·도형은
보이는 그대로 들어가지만 레이어는 남지 않는다.
원본 macOS판도 같다. 원본의 내보내기는 PNG와 JPEG 두 가지뿐이고(`ImageExporter.swift`), PSD 내보내기는 없다.

레이어를 살려 포토샵으로 넘기려면 PSD 내보내기가 따로 필요하다. 레이어 픽셀, 위치, 불투명도, 혼합 모드,
마스크, 그룹, 클리핑은 PSD에 대응하는 구조가 있다. 반면 편집 가능한 텍스트(PSD의 문자 레이어 데이터)와
레이어 효과 설정은 형식이 복잡하다. 그래서 1차는 텍스트와 효과를 픽셀로 굳혀 넣는 방식이 현실적이다(13.7).

### 14.3 구조

```
Core/Format/Psd/
├─ PsdBinary.cs      빅엔디안 읽기·쓰기, PackBits·ZIP·예측 압축 풀기
├─ PsdFile.cs        헤더·리소스·레이어 레코드·추가 블록 해석(채널은 필요할 때 디코딩)
├─ PsdDescriptor.cs  Photoshop 기술자(descriptor) 읽기·쓰기 — 레이어 효과용
├─ PsdMapping.cs     혼합 모드·조정 레이어 5종·효과 3종 대응, PsdNote
├─ PsdImport.cs      PSD → CanvasDocument
└─ PsdExport.cs      CanvasDocument → PSD
```

셸은 `DocumentFiles`가 확장자로 나눈다. `.psd`로 연 문서는 저장하면 그 PSD에 다시 쓴다(`.psb`는 쓰지 않으므로
다른 이름으로 저장을 묻는다). 다른 이름으로 저장은 PSD를 먼저 보여 주고, 이미 `.comp`인 문서만 `.comp`를 먼저
보여 준다. 저장은 `.partial` 파일에 다 쓴 뒤 바꿔치기해서, 도중에 실패해도 원래 파일이 깨지지 않는다.

### 14.4 설계에서 정한 것과 이유

- **파일 전체를 메모리에 읽고, 채널은 필요할 때 푼다.** PSD의 길이 필드가 32비트라 파일이 2GiB를 넘지 않는다.
  레코드를 다 읽은 뒤에 채널을 풀어야 하므로 스트리밍 이점이 없다.
- **16·32비트는 `Lr16`/`Lr32` 블록에서 읽는다.** 이 깊이에서는 레이어 정보가 문서 수준 블록에 따로 있다(길이 접두 없음).
  32비트는 선형광이라 색 채널만 sRGB로 인코딩하고 알파·마스크는 그대로 둔다.
- **내보낼 때 레이어를 문서 격자에 한 장씩 그린다.** 이 프로그램의 레이어는 픽셀을 다시 만들지 않고 배치만
  바꾸지만(비파괴 변환), PSD 레이어는 문서 격자 위 픽셀이다. 레이어가 닿는 사각형만 그려서 메모리를 아낀다.
- **효과는 Photoshop이 쓰는 키를 순서까지 그대로 쓴다.** Photoshop 샘플의 `lfx2`를 덤프해서 그대로 따랐다.
  Photoshop은 크기에 효과 배율(`Scl `)을 곱하고, 스프레드(`Ckmt`)는 단위가 픽셀로 적혀 있어도 값은 퍼센트다.
- **그룹 불투명도·혼합 모드는 합쳐서 가져온다.** 이 프로그램의 폴더는 원본처럼 늘 통과 그룹이라 따로 합성하는
  그룹을 표현할 수 없다. 합친 레이어가 그룹의 불투명도·모드·마스크·효과를 가진다.
- **채우기 불투명도는 픽셀에 곱한다.** 채우기 불투명도는 내용만 흐리고 효과는 두는 값이라, 픽셀 알파에 곱하면
  정확히 같다. 이 프로그램의 불투명도는 둘 다 흐리므로 거기에 넣으면 안 된다.
- **숨긴 기준 레이어의 클립 레이어도 숨긴다.** Photoshop은 기준을 숨기면 클리핑 그룹 전체가 사라지지만 여기서는
  숨긴 기준도 클립에 쓰인다. 같은 모습이 되도록 클립 레이어를 숨긴다.
- **폴더·조정 레이어의 마스크는 Photoshop이 저장한 사각형만 쓴다.** 둘레에 기본값 1픽셀 테두리를 두르고 문서에
  배치한다. 이 프로그램은 떨어져 놓인 마스크의 바깥을 가장자리 값(`Beyond()`)으로 보여 주므로 결과가 같다.
  큰 캔버스의 작은 마스크가 캔버스 크기로 커지지 않는다.
- **합성 이미지의 흰 매트.** Photoshop은 투명한 문서의 합성 이미지를 흰색 위에 저장한다. 읽을 때는 흰색을 빼고,
  쓸 때는 흰색을 입힌다.
- **화면 문구에 Photoshop 이름을 쓰지 않는다.** 제3자 고지의 상표 원칙대로 "PSD 문서", "PSD로 내보내기"로 썼다.

### 14.5 검증

**Photoshop이 저장한 파일 36개**(psd-tools 테스트 자료, MIT, `tests/.../Fixtures/psd`)로 확인했다. 모든 PSD에는
Photoshop이 직접 합성한 이미지가 들어 있다. 그래서 가져온 레이어를 이 프로그램이 합성한 결과를 그 이미지와 비교하면
Photoshop 없이도 "Photoshop에서 보이던 대로 열렸는지"를 픽셀로 잴 수 있다.

- 그룹, 클리핑, 마스크(켬·끔), 숨김, 불투명도, 채우기 레이어, 16·32비트, PSB, 회색조, 문자, 고급 개체, Levels,
  Exposure, 혼합 모드 10종(곱하기·스크린·오버레이·색상 닷지·색상 번·차이·색조·색상·광도·통과) 등 29개가
  **채널 평균 차이 2.5 이하, 16 넘게 다른 픽셀 2% 이하**로 Photoshop과 같다.
- 내보내기는 세 겹으로 확인한다. ① 다시 가져와서 원래 문서와 합성 비교, ② 구조(이름·폴더·클리핑·조정 값·효과
  값) 비교, ③ CI에서 **psd-tools**(독립 구현체)로 우리가 쓴 PSD를 열어 레이어 종류·클리핑·마스크·효과를 확인하고,
  psd-tools가 레이어로 다시 합성한 결과를 우리가 저장한 합성 이미지와 비교(`scripts/check_psd.py`).
- Photoshop 파일 31개를 가져와서 → 내보내고 → 다시 가져와도 같은 모습인지 확인한다.
- 셸 자체검사(`FilesCheck`): 프로젝트를 PSD로 저장 → 열기(새 탭, 같은 이름·레이어 수, 픽셀 차이 2 이하) →
  끌어다 놓기(새 탭).

**Curves와 Hue/Saturation은 값은 정확히 옮기지만 그리는 방식이 Photoshop과 다르다.** 첫 CI에서 이 두 파일만
평균 차이 10.2, 17.6이었다. 원인을 가르려고 psd-tools로 두 가지를 쟀다.

| 비교 | Curves | Hue/Saturation |
|---|---|---|
| Photoshop vs 조정 레이어를 뺀 합성 | 27.35 | 27.19 |
| Photoshop vs 이 프로그램 | 10.2 | 17.6 |
| Photoshop vs psd-tools(자연 3차 스플라인) | 0.58 | 0.66 |
| Photoshop vs psd-tools를 단조 보간으로 바꾼 것 | 5.92 | — |

조정은 적용되고 있다(27 → 10·18). 차이는 계산 방식에서 온다. Curves는 원본 Compositor가 튀지 않는 단조 보간을
쓰고 Photoshop은 자연 스플라인을 써서, 보간만 바꿔도 5.9가 생긴다. Hue/Saturation은 원본의 33점 색 큐브 근사가
강한 범위 설정(채도 93, 밝기 −91 등)에서 Photoshop과 멀어진다. 둘 다 파일을 읽는 문제가 아니라 **원본에서 물려받은
조정 엔진의 문제**다. 이걸 Photoshop에 맞추면 macOS판과 같은 `.comp`가 다르게 보이게 되므로 사용자 결정으로
남겼다(14.6). 테스트는 지금 거리를 상한으로 둬서 더 나빠지면 잡히게 했다.

### 14.6 남은 것

- **실제 Photoshop에서 열어 보기.** psd-tools는 통과했지만 Photoshop 자체로는 아직 열어 보지 못했다. 특히 편집 가능한
  효과(`lfx2`)와 조정 레이어가 Photoshop에서 제대로 편집되는지 사용자 PC에서 확인해야 한다.
- **Curves·Hue/Saturation 계산 방식**(14.5): Photoshop에 맞출지, macOS판 호환을 지킬지 결정이 필요하다.
- **혼합 모드 추가**: 소프트 라이트, 하드 라이트, 선형 닷지, 선형 번, 제외, 빼기, 나누기 등. Direct2D 혼합 효과는 모두
  지원하지만 소프트웨어 렌더러와 `.comp` 형식(원본은 모르는 값)을 함께 넓혀야 한다.
- **편집 가능한 문자 레이어 주고받기**(PSD의 `TySh`·EngineData), 벡터 마스크, 스마트 오브젝트 원본, 레이어 효과 나머지.
- **16비트 저장, PSB 쓰기, ICC 색 프로필**(CMYK·Lab은 지금 프로필 없이 단순 변환).

## 15. MCP 서버 — AI가 편집기를 도구로 쓰기 (2026-09-24)

### 15.1 왜 했나

13절의 포스터 분석 뒤 사용자 요청은 "AI가 이 편집기로 포스터를 만들 수 있게 하자"였다. 인물 사진처럼 Claude가
그릴 수 없는 것은 **Codex의 이미지 생성(`$imagegen`)을 부르는 명령도 포함**하라는 요청이 같이 있었다. 그리고
"다 테스트해 본 뒤 실제로 포스터를 재현하는 테스트를 하자"는 순서였다. 이후 "Photoshop과의 실제 테스트는
향후 과제로 남기고 MCP를 완벽하게 구현하자"는 요청에 따라 이 절의 작업을 했다. 사용 설명은
[`mcp.md`](mcp.md)에 있다.

| 묶음 | 상태 | 커밋 |
|---|---|---|
| 텍스트 배치를 Core로 옮김(`TextPlacement`) — 셸과 MCP가 같은 코드 | 완료 | `60a2bbd` |
| Core: 세션·도구 34개·JSON-RPC 서버, 테스트 10개 | 완료 | `60a2bbd`, `1bd1cd9`, `6a06c4a`, `b642966` |
| 셸: `--mcp` 진입점(DirectWrite 글꼴, WIC 해독, JPEG, AI 배경 제거, 이미지 생성기) | 완료 | `60a2bbd` |
| CI: 실제 exe를 MCP 클라이언트로 조종해 포스터 만들기 + psd-tools 검사 | 완료 | `60a2bbd`, `7a47da7` |
| 실제 Claude Code·Codex에 등록해 써 보기, 실제 Codex 이미지 생성 | **남음** (15.6) | — |

### 15.2 구조

```
Core/Automation/
├─ McpJson.cs          도구 결과(텍스트·PNG), 느슨한 인자 읽기(숫자 문자열·"#RGB"·{x,y} 등), 스키마 빌더
├─ EditorServices.cs   셸이 꽂아 주는 것: 글꼴, 이미지 해독·JPEG, 배경 제거 모델, 이미지 생성기
│                      이미지 생성기 3종(명령 템플릿·OpenAI API·Codex CLI)과 환경 변수로 고르기
├─ EditorSession.cs    열린 문서들(doc1, doc2…)과 문서마다의 실행 취소 기록(픽셀 소유)
├─ McpTools.cs         문서·보기·기록 도구
├─ McpLayerTools.cs    레이어 만들기·다루기 도구
├─ McpEffectTools.cs   클리핑·마스크·효과·조정·필터·배경 제거·이미지 생성
└─ McpServer.cs        JSON-RPC 2.0(initialize, tools/list, tools/call, ping), 줄 단위 stdio
Shell/McpHost.cs       --mcp: 창 없이 표준 입출력(UTF-8, BOM 없음)으로 서버 실행
```

도구 34개의 목록과 인자는 `mcp.md` 2절, 그리고 `tools/list`의 스키마가 원본이다.

### 15.3 설계에서 정한 것과 이유

- **서버는 Core에 둔다.** 도구는 편집기와 같은 명령(`LayerCommands`, `ShapeTool`, `TextPlacement`, 효과·조정 설정)을
  부르므로 AI가 만든 레이어는 사람이 만든 것과 같고, 편집기에서 편집 가능한 상태로 열린다. 그리고 전부 백엔드·
  디스플레이 없이 테스트된다. 셸은 글꼴·코덱·AI 모델처럼 윈도우에만 있는 것을 `IEditorServices`로 꽂아 줄 뿐이다.
- **별도 프로그램이 아니라 같은 exe의 `--mcp`.** 설치본 하나로 끝나고, 글꼴·배경 제거 모델을 그대로 쓴다.
  실행 중인 창에 붙는 방식(편집기를 보면서 AI가 작업)은 창과 동시 편집·잠금 설계가 따로 필요해 뒤로 미뤘다(15.6).
- **결과를 눈으로 볼 수 있게 `render`가 PNG를 돌려준다.** 모델이 레이어 JSON만 보고는 겹침·잘림을 판단하지 못한다.
  문서·레이어·영역을 `max_size`로 줄여 돌려줘서 토큰을 아낀다.
- **텍스트 좌표는 첫 줄 기준선.** 디자이너가 글자를 놓는 방식과 같고, 글꼴마다 다른 위 여백에 흔들리지 않는다.
- **인자는 느슨하게 받는다.** 모델은 `"48"`, `"#fff"`, `[x, y]`, `50`(%)처럼 조금씩 다르게 보낸다. 뜻이 분명하면
  받아들이고, 모르는 값은 무엇이 가능한지 적어서 `isError`로 돌려준다. JSON-RPC 오류로 끊지 않아야 모델이 고쳐서
  다시 부를 수 있다.
- **이미지 생성기는 순서대로 찾는다.** `COMPOSITOR_IMAGE_COMMAND` → `OPENAI_API_KEY`(기본 `gpt-image-2`) →
  `PATH`의 `codex`(`codex exec`에 `$imagegen`으로 지정 경로에 PNG를 저장하라고 시킴). `COMPOSITOR_IMAGE_GENERATOR`로
  강제할 수 있다. 생성기가 다른 파일 이름으로 저장해도 작업 폴더의 가장 새 이미지를 받는다. 5분 제한.
- **생성 크기와 배치 크기를 나눈다.** `generate_image`의 `width`·`height`는 만들 그림의 크기이고, 배치는 `x`·`y`·
  `fit`으로 한다. 처음에는 둘을 같이 써서 `fit`이 무시됐다(`b642966`).
- **실행 취소 기록은 문서마다, 픽셀 소유.** 편집기와 같은 `DocumentHistory(ownsPixels: true)`라 되돌려서 버려진
  픽셀이 해제된다. 누수 검사 테스트가 포스터 하나를 만들고 닫은 뒤 살아 있는 버퍼가 0인지 본다.

### 15.4 검증

- **Core 테스트 10개**(`McpTests`): 핸드셰이크·프로토콜 버전 협상, 잘못된 요청·모르는 도구, 실패한 도구 뒤에도 세션이 이어지는지, 포스터 한 장을 도구로
  만들기(텍스트 뒤틀기·클리핑·마스크·효과·조정), 텍스트 고치기, 실행 취소/다시 실행, 순서 바꾸기, 이미지 생성(가짜
  생성기), 명령 템플릿 채우기·OpenAI 크기 고르기, 버퍼 누수.
- **CI에서 실제 exe로 포스터 만들기**(`scripts/mcp_poster.py`, "Make a poster through MCP" 단계). 파이썬 MCP 클라이언트가
  게시된 AI 포함판을 `--mcp`로 띄우고, 모델이 보는 도구만으로 1080×1350 포스터를 만든다: 그라디언트로 칠하고 마스크로
  흐려지는 BRUTALISM, 노랑→초록 패널(클리핑 그라디언트 + 드롭 섀도), 생성한 인물(배경 제거 + 흑백 + 레벨), 뒤집힌
  EXHIBITION, 아치형 "Choose Your Style", 세로 FREE ENTRY, 별 셋, 선, 한글. 그다음 `render`로 보고, PSD·COMP·PNG·JPEG로
  저장하고, COMP를 다시 열어 레이어 수를 확인한다. 저장한 PSD는 `check_psd.py`(psd-tools)가 다시 검사한다.
- 손으로 돌린 실행(workflow_dispatch)은 결과 그림을 `mcp-results` 브랜치에 올려서 아티팩트를 받지 않고도 볼 수 있다.

**인물 사진을 받아 오지 않고 그린다.** 처음에는 CI가 위키미디어 공용의 퍼블릭 도메인 인물 사진을 파일 이름으로
받아 썼는데, 그 이름의 실제 사진이 이름과 달리 공개 저장소에 올리기에 부적절한 누드 사진이었다. 그 포스터가
`mcp-results`에 올라갔다(`CI 35959829715`). 그래서 `7a47da7`부터는 `COMPOSITOR_IMAGE_COMMAND`를
`scripts/stand_in_image.py`(단순한 흉상을 그리는 스크립트)로 두고 `generate_image`로 인물을 만든다. 내용을 아무도 확인하지
않은 외부 사진이 공개 결과물에 들어가지 않고, 덤으로 명령 템플릿 생성기 경로 전체가 CI에서 돈다.
**앞의 커밋은 `mcp-results` 브랜치 기록에 남을 수 있으니 저장소 관리자가 그 브랜치를 지우거나 정리해야 한다.**

### 15.5 사용 흐름

1. 설치한 exe를 Claude Code·Codex·Claude Desktop에 MCP 서버로 등록한다(`mcp.md` 1절).
2. "1080×1350 전시 포스터를 만들어 줘"처럼 요청하면 모델이 `new_document` → `add_text`·`add_shape`·`add_gradient`
   → `set_clipping`·`set_mask`·`set_effects` → `render`로 확인 → 고치기 → `save_document`로 진행한다.
3. 사진이 필요하면 `generate_image`(Codex `$imagegen` 등)로 만들거나 `add_image`로 넣는다.
4. 저장한 `.psd`나 `.comp`를 편집기에서 열어 사람이 이어서 다듬는다.

### 15.6 남은 것

- **실제 AI 클라이언트에서 써 보기.** 프로토콜은 테스트와 CI 클라이언트로 확인했지만, Claude Code·Codex에 등록해
  실제 모델이 포스터를 만드는 것은 사용자 PC에서 확인해야 한다.
- **실제 Codex 이미지 생성.** CI에는 Codex 로그인이 없어 명령 템플릿 경로를 대역 스크립트로만 돌렸다. `codex exec`가
  `$imagegen`으로 지정 경로에 저장하는지 실제로 확인해야 한다.
- **실행 중인 편집기에 붙기.** 지금은 창 없는 별도 프로세스라, 작업 결과는 파일로 넘어간다. 열린 창에서 AI 작업을
  실시간으로 보려면 창 프로세스와의 연결(이름 있는 파이프 등)과 동시 편집 규칙이 필요하다.
- **Photoshop 실제 테스트**(14.6과 같음): 사용자 요청대로 향후 과제로 둔다. MCP로 만든 PSD도 대상이다.

## 16. M8 이후 기능 실사용 확인과 우클릭 메뉴 (2026-09-24)

최신 `main`(`bf29333`) CI 결과물(AI 포함판, 설치 없이 압축 해제본)을 이 PC에서 띄워 12절과 같은 방식(PowerShell

### 16.1 실제 입력으로 정상 확인한 것

T로 문자 도구, 클릭한 곳이 기준선인 새 텍스트 레이어, 한글·영문 입력과 레이어 이름, Enter 여러 줄, Ctrl+Enter 확정,
한 번의 실행 취소·다시 실행, 옵션 바의 크기·굵게·가운데 정렬(기준점 유지), 이동 도구로 텍스트 레이어 이동, 뒤틀기
창 15종 목록과 미리보기·적용(부채꼴), 레이어 스타일 창(사용자 확인), 선택 영역 Delete 지우기(이미지·텍스트 레이어),
Ctrl+Shift+I 반전 후 바깥 지우기.

### 16.2 찾아서 고친 것

| 증상 | 원인 | 수정 |
|---|---|---|
| 뒤틀기·레이어 스타일 창의 단위가 `{0}%` | 값을 넣는 형식 문구(`UnitPercent`)를 단위로만 씀 | 다른 창처럼 `%` |
| 드롭다운 목록이 우클릭 메뉴처럼 포인터 자리에 뜸 | 모든 목록이 `Chrome.Popup` 한 곳에서 포인터 위치에 띄움 | 컨트롤 클릭으로 열면 그 컨트롤 아래에(`Ui.Clicked`, 공간이 없으면 위로). 글꼴·혼합 모드·캔버스 확장·색 범위·뒤틀기 목록 모두 |
| 초보자가 단축키를 몰라 선택 영역으로 아무것도 못 함 | 캔버스에 우클릭 메뉴가 없음(원본 macOS판도 없음) | 캔버스 우클릭 메뉴 추가(16.3) |

### 16.3 캔버스 우클릭 메뉴

사용자 요청으로 넣었다. 포토샵처럼 선택 영역이 있으면 선택 영역에 할 일(선택 해제, 반전, 선택 영역 변형, 복사한·잘라낸
레이어, 잘라내기·복사·붙여넣기, 칠하기, 내용 인식 채우기, 지우기)을, 없으면 레이어 기본 명령(모두 선택, 레이어 픽셀
선택, 붙여넣기, 새 레이어, 복제, 변형, 삭제)을 보여 준다. 맨 위에 실행 취소·다시 실행, 맨 아래에 레이어 스타일·문자
래스터화가 있다.

- **항목은 전부 메뉴 막대의 명령이다**(`AppCommands.CanvasMenu`, `MenuBar.Popup`). 이름·단축키·비활성 표시를 메뉴
  막대와 같은 코드로 만들고 갱신하므로, 우클릭으로만 되는 기능이나 메뉴와 다르게 동작하는 항목이 생기지 않는다.
  옆에 단축키가 보여서 익히는 데도 쓰인다. 자체검사(`MenuCheck`)가 항목마다 실제 명령인지 확인한다.
- **브러시 계열 도구는 원본대로 우클릭 드래그가 크기 조절이다.** 그래서 누른 자리에서 4픽셀 안에 뗀 것만 클릭으로 보고
  메뉴를 띄우며, 그 사이의 흔들림으로 바뀐 크기는 되돌린다(`CancelBrushAdjust`). 왼쪽 버튼을 누른 채(획·드래그 도중)
  누른 우클릭은 메뉴를 띄우지 않는다.
- 창(시트)이 열려 있는 동안에는 메뉴 막대처럼 띄우지 않는다. 레이어 패널의 줄 우클릭 메뉴는 그대로다.

### 16.4 복제 도장의 원본 표시

사용자가 "Alt로 원본을 찍고 다른 곳을 클릭해도 표시가 안 나오고 느리게 반응하며 변화가 없다"고 알렸다. 재현해 보니
칠하기 자체는 되지만 **화면에 원본을 알려 주는 표시가 전혀 없었다.** 원본 macOS판(`BrushCursorOverlay`)에 있는
두 가지를 옮기지 않았던 것이다.

- **원본 십자 표시.** Alt+클릭한 곳에 나타나고, 획 도중(정렬이면 획 사이에도)은 붓 위치에 오프셋을 더한 곳을 따라간다.
  원본의 `cloneSamplePoint`와 같은 규칙이다.
- **원 안 미리보기.** 획 사이에 붓 원 안에 클릭하면 찍힐 모습을 브러시 불투명도로 보여 준다. Alt를 누른 동안(새 원본을
  고르는 중)과 획 도중에는 숨긴다. 원본은 원 가장자리를 경도에 맞춰 부드럽게 하는데, 여기서는 원의 경계 그대로 둔다.
- 미리보기의 원본은 획이 실제로 복사하는 것과 같다. 레이어 자신의 픽셀, "모든 레이어 샘플링"이면 합성 결과다. 합성은
  문서 상태마다 한 번만 만들고, GPU에는 원 아래 정사각형만 올리며 그것도 위치가 바뀔 때만 다시 올린다.

"변화가 없다"는 다른 원인일 수도 있다. 샘플링을 끈 채 빈 레이어나 일부만 있는 레이어가 골라져 있으면 그 레이어의 빈
곳을 복사하므로 칠해도 달라지지 않는다. 이제는 미리보기가 비어 보이므로 알아챌 수 있다.

### 16.5 제목 표시줄과 메뉴 막대를 어둡게

사용자 요청으로 창 맨 위의 흰 띠(제목 표시줄, 메뉴 막대)를 옵션 바와 같은 색(`Ui.Panel`)으로 바꿨다(`DarkFrame`).

- 제목 표시줄은 DWM 속성(`DWMWA_USE_IMMERSIVE_DARK_MODE`, 윈도우 11은 `DWMWA_CAPTION_COLOR`로 정확한 색)으로 한다.
- 메뉴 막대는 다크 모드에서도 흰색으로 남는다. Notepad++ 등이 쓰는 방식대로 uxtheme가 막대를 그리기 전에 보내는
  비공개 메시지 `WM_UAHDRAWMENU`·`WM_UAHDRAWMENUITEM`에 답해 배경과 제목을 직접 칠하고, 막대 아래 1픽셀 흰 줄을 덮는다.
  비공개지만 비스타 이후 바뀐 적이 없고, 보내지 않게 되더라도 막대가 다시 밝게 그려질 뿐이다.
- 막대는 여전히 네이티브 메뉴라 키보드 탐색·접근성·한글 표시는 그대로다. 막대에서 열리는 메뉴 목록은 시스템 색(밝은색)이다.

### 16.6 남은 것

- 도형 확장(다각형·별·선·외곽선)과 PSD 가져오기·내보내기의 실제 입력 확인.
- 우클릭 메뉴·드롭다운 위치·복제 도장 표시·어두운 제목/메뉴 막대를 새 빌드에서 실제 입력으로 확인.

## 17. 포토샵의 변형·뒤틀기·유동화·왜곡 필터 (2026-09-24)

사용자 요청으로 네 가지를 넣었다. 모두 원본 macOS판에는 없는 포토샵 기능이다.

| 묶음 | 내용 | 커밋 |
|---|---|---|
| 필터 → 왜곡 | 핀치, 구형화, 돌리기, 파형, 극좌표 | `a5b4298` |
| Core | 기울이기·원근 드래그, 뒤틀기 격자(`WarpMesh`), 유동화 변위장(`LiquifyField`), 테스트 | `409c30b` |
| 셸 | 편집 → 변형 하위 메뉴, 이동 도구의 변형 방식 목록, 뒤틀기·유동화 세션과 옵션 바, 우클릭 메뉴, 자체검사 | 이 절의 커밋 |

### 17.1 편집 → 변형

비율, 회전, 기울이기, 왜곡, 원근, 뒤틀기, 180° 회전, 90° 시계 방향·반대 방향 회전, 가로·세로 뒤집기. 캔버스
우클릭 메뉴에도 같은 하위 메뉴가 있고, 이동 도구 옵션 바 맨 앞에 "크기·회전 ▾" 목록으로도 고를 수 있다.

- **기울이기·왜곡·원근은 이동 도구 핸들의 모드다.** 전에는 Ctrl을 누른 채 핸들을 끌어야만 왜곡이 됐다. 이제 메뉴로
  모드를 고르면 Ctrl 없이 핸들이 그렇게 움직인다. 모드는 Enter·Esc·다른 도구로 끝난다.
- 기울이기는 변은 변 방향으로, 꼭짓점은 드래그와 더 가까운 변 방향으로만 미끄러진다. 원근은 꼭짓점을 그 변 방향으로
  옮기면서 변의 반대쪽 끝을 같은 만큼 반대로 옮긴다(변이 가운데를 기준으로 넓어지거나 좁아짐). 둘 다 왜곡처럼 드래그가
  끝날 때 픽셀을 다시 샘플링한다(`QuadWarp`).
- 90°·180° 회전은 배치(6개 숫자)만 바꾸므로 픽셀을 건드리지 않는다. 여러 레이어는 함께 둘러싼 상자의 가운데를 기준으로 돈다.

### 17.2 뒤틀기(격자)

포토샵과 같은 4×4 베지어 패치다(`WarpMesh`). 모서리 점(핸들 2개를 함께 끌고 감), 핸들, 안쪽 점을 끌거나 **그림 자체를
끌 수 있다.** 그림을 끌면 잡은 지점이 정확히 포인터를 따라가도록 16개 점을 각자 영향만큼 옮긴다(최소 변경 해).
옵션 바의 스타일 목록에서 텍스트 뒤틀기의 15가지 모양으로 격자를 시작할 수 있고 구부리기를 조절할 수 있다.

- 패치는 역함수가 없어서 작은 삼각형들로 잘라 각각 아핀 변환으로 원본을 읽는다. 결과를 행 묶음으로 나눠 병렬로
  채우므로 작업 순서와 무관하게 같은 결과가 나온다.
- 세션 동안에는 문서가 멈춘다(메뉴가 회색). 화면은 줌에 맞는 축소 단계로 창 안만 그린다(`WarpPreview`). Enter·확인은
  한 기록으로 적용, Esc·취소는 기록 없이 되돌린다. 레이어와 같은 격자의 연결된 마스크는 함께 휜다.

### 17.3 필터 → 픽셀 유동화 (Ctrl+Shift+X)

포토샵처럼 픽셀을 직접 바꾸지 않고 **역방향 변위장**을 쌓는다(`LiquifyField`). 결과는 언제나 원본을 한 번만 다시
샘플링한 것이라 여러 번 문질러도 흐려지지 않고, 재구성이 원래 모습을 그려 되돌릴 수 있다.

- 브러시: 뒤틀기(W), 재구성(R), 돌리기(C, Alt로 반대), 오목(S), 볼록(B), 왼쪽 밀기(O), 고정(F), 고정 해제(D).
  `[` `]`로 크기, 옵션 바에서 크기·압력·모두 복구·확인·취소.
- 돌리기·오목·볼록·재구성·고정은 마우스를 멈춰 누르고 있어도 계속 작용한다(가장자리 자동 스크롤과 같은 타이머).
- 고정된 곳은 화면에 반투명 빨강으로 보인다. 변위장은 큰 레이어에서 몇 픽셀 간격 격자(최대 약 100만 점)에 두고 사이를
  보간한다. 붓이 격자 간격보다 훨씬 커서 모든 픽셀에 둔 것과 차이가 없다.
- 흐림 효과 도구의 "픽셀 유동화" 모드(원본 기능, 픽셀을 직접 밂)는 그대로 둔다.

### 17.4 필터 → 왜곡

핀치·구형화(양 −100~100), 돌리기(각도 −999~999°), 파형(파장·진폭, 레이어 픽셀), 극좌표(직교↔극). 모두 목적 픽셀에서
원본 위치를 거꾸로 계산해 읽는다. 핀치·구형화·극좌표는 레이어에 내접하는 타원 안에서, 돌리기는 내접원 안에서 작용한다.
미리보기는 렌즈 교정처럼 레이어 전체를 축소 단계로 돌린다.

### 17.5 검증

Core 테스트: 기울이기·원근 모서리 계산, 평평한 격자가 그림을 그대로 두는지, 그림 끌기가 잡은 점을 정확히 옮기는지, 모서리가
핸들을 끌고 가는지, 유동화 각 브러시의 방향·고정·재구성, 왜곡 필터 각각의 방향과 미리보기=적용. 셸 자체검사(`ToolsCheck`):
뒤틀기 격자가 문서를 멈추는지, 손대지 않은 격자는 기록을 남기지 않는지, 아치로 휜 격자가 한 기록이고 실행 취소되는지,
Esc, 기울이기 모드와 Esc, 90° 회전이 배치만 바꾸는지, 유동화 뒤틀기 한 획이 한 기록인지. `MenuCheck`는 새 명령을
모두 실행하고 세션은 Enter로 닫는다.

### 17.6 남은 것

- 실제 마우스로 격자 점·그림 끌기, 유동화 브러시 감각(압력·간격) 확인.
- 포토샵에 있지만 뺀 것: 유동화의 매끄럽게·얼굴 인식 도구, 뒤틀기 격자 분할(3×3보다 촘촘한 격자), 원근 뒤틀기, 퍼펫 뒤틀기.

## 18. PSD 문자 레이어를 고칠 수 있는 텍스트로 (2026-09-24)

사용자가 템플릿 PSD(`9284159.psd`, 문자 레이어 23개)를 열었더니 모든 문자가 픽셀로만 들어와 고칠 수 없었다.
포토샵 텍스트 엔진(Adobe Text Engine)은 포토샵 안에만 있는 비공개 기술이라 가져다 쓸 수 없다. 사용자와 정한 방향은
두 가지다. **고치기 전까지는 포토샵이 그린 모습 그대로 두고**, **다시 그릴 때는 포토샵의 배치 규칙에 최대한 맞춘다.**

### 18.1 가져오기

- `TySh` 블록의 기술자에서 변형 행렬·뒤틀기·`EngineData`를 읽고, `EngineData`(텍스트 엔진 고유의 PostScript 비슷한
  사전)를 해석해 글자, 글꼴(PostScript 이름), 크기, 자간, 행간, 색, 정렬, 가짜 굵게·기울임, 모두 대문자를 꺼낸다
  (`PsdType`, `EngineData`). 스타일 런의 값은 문서의 기본 스타일 위에 덮어쓴 것이라 둘을 합쳐 읽는다.
- 레이어의 래스터는 **포토샵이 저장한 픽셀 그대로**이고, 텍스트 레시피의 `Rendered`가 그 버퍼를 가리키므로 살아 있는
  텍스트다. 글자를 고치는 순간부터 이 편집기의 엔진으로 다시 그린다. 기준점은 포토샵의 텍스트 원점(첫 기준선의 시작)이다.
- 변형 행렬의 균일한 배율은 글자 크기에 곱한다(포토샵 문자 패널에 보이는 값). 회전·기울어진 문자, 글상자(영역) 문자,
  칠 불투명도가 100%가 아닌 문자는 지금처럼 픽셀로 둔다.
- 이 편집기의 텍스트는 레이어 전체가 한 서식이라, 런마다 서식이 다르면 가장 많은 글자를 덮는 서식을 쓰고 알린다
  (`TypeSimplified`). 가로·세로 비율, 기준선 이동, 밑줄·취소선, 작은 대문자, 수동 커닝도 옮기지 못해 같이 알린다.
- 글꼴은 PostScript 이름으로 설치된 패밀리를 찾는다(`PsdFonts`): 영문자·숫자만 비교해 가장 긴 접두 일치를 고르고
  (`ArialMT` → Arial, `MalgunGothicBold` → 맑은 고딕 굵게), 뒤쪽 스타일 이름에서 굵기·기울임을 읽는다. 설치되지 않았으면
  이름을 띄어 써서 패밀리를 추정하고(`WixMadeforDisplay` → Wix Madefor Display) 알림에 설치할 글꼴 이름을 보여 준다.

### 18.2 포토샵 배치 규칙 맞추기

기준선 위치(원점 = 첫 기준선), 자간 단위(1/1000em, 글자마다 뒤에), 자동 행간 120%는 이미 같았다. 빠져 있던 것은
**커닝**이다. 포토샵 기본값("메트릭")은 글꼴 자신의 쌍 커닝이라, 없으면 "AV", "To", "Wa"가 벌어져 고치자마자 글줄이
넓어진다. GPOS 표의 `kern` 기능(쌍 위치 조정, 형식 1·2, 확장 룩업 포함)과 옛 `kern` 표를 읽는 `FontKerning`을 Core에
넣고, 셸은 DirectWrite의 `TryGetFontTable`로 표를 넘긴다. 레이아웃은 커닝을 자간보다 먼저 더한다(포토샵과 같은 순서).
이 편집기에서 새로 만드는 텍스트도 이제 커닝된다.

### 18.3 남은 것

- 샘플 PSD의 글꼴(Wix Madefor Display)을 설치한 뒤, 고치기 전(포토샵 픽셀)과 고친 뒤(우리 엔진)를 겹쳐 비교해 차이를 잰다.
- PSD로 다시 저장하면 문자 레이어는 여전히 픽셀로 저장된다(`TextExportedAsPixels`). 포토샵에서 고칠 수 있게 쓰려면
  `TySh`와 `EngineData` 쓰기가 필요하다.
- 글자별 서식, 글상자 줄바꿈, 회전된 문자.

## 19. 대형 복제 도장·픽셀 유동화 지연 제거 (2026-09-24)

큰 브러시와 큰 문서에서 입력이 멈추던 경로를 전체 이미지 복사 방식에서 타일·dirty rectangle 방식으로 바꿨다. GPU가 있으면 Direct2D 비트맵을 계속 재사용하고, GPU가 없거나 WARP로 실행되는 환경에서도 같은 영역 단위 CPU 경로를 사용한다.

- Alt+클릭으로 복제 원본을 지정하면 즉시 다시 그리며, 원본 십자 표시는 미리보기보다 위에 그린다.
- 복제 미리보기는 포인터가 움직일 때마다 브러시 크기의 픽셀을 복사하고 업로드하지 않는다. 256×256 원본 타일을 필요한 순간 한 번 만들고 GPU 비트맵으로 캐시한다.
- “모든 레이어 샘플링”은 전체 문서를 먼저 합성하지 않는다. 현재 요청된 원본 타일이 참조하는 문서 영역만 소프트웨어 합성하고 타깃 레이어 좌표로 변환한다.
- 큰 브러시 팁은 설정별로 캐시하며 팁 생성과 서로 독립인 타일 페인팅을 CPU 코어에 병렬 분배한다. 작은 브러시는 병렬 예약 비용을 피한다.
- 유동화 미리보기는 세션 전용 픽셀 버퍼와 GPU 비트맵을 유지한다. 변형된 사각형만 다시 계산하고 `CopyFromMemory`로 같은 GPU 비트맵의 해당 부분만 갱신한다.
- 유동화 dab 계산 배열을 브러시 이동마다 만들지 않고 재사용한다. 한 프레임 동안 쌓인 포인터 이동은 최신 좌표 하나로 병합하되, 브러시 간격 보간으로 스트로크 연속성은 유지한다.
- 브러시 종료 시 전체 레이어 `Flatten()`을 하지 않는다. 기존 불변 버퍼와 바뀐 타일을 가진 지연 `PixelBuffer`로 커밋하고, 화면·다음 스트로크는 필요한 영역만 펼친다. 내보내기나 전체 이미지 필터가 연속 메모리를 요구할 때만 한 번 물질화한다.

Core 회귀 테스트는 지연 커밋이 영역 복사 때문에 전체 펼침으로 바뀌지 않는지, 모든 레이어 복제가 부분 타일만 반환하는지, 유동화 미리보기가 같은 버퍼를 유지하면서 부분 dirty rectangle을 보고하는지 확인한다.

## 20. 이미지 가져오기와 캔버스 크기 자동 조정 (2026-09-24)

이미지를 레이어로 가져올 때 문서 상태에 따라 배치 규칙을 다르게 적용한다. 원본 픽셀 버퍼는 리샘플링하지 않고 레이어의 비파괴 변형 크기만 조정한다.

- 한 번도 편집하지 않은 빈 투명 캔버스에 처음 이미지를 가져오면 캔버스 너비와 높이를 이미지 원본과 똑같이 맞춘다. 기본 빈 레이어는 남기지 않고 가져온 이미지가 유일한 레이어가 된다.
- 첫 이미지 이후에는 가져온 이미지가 캔버스보다 큰 경우에만 종횡비를 유지해 캔버스 안에 맞춘다. 이미 작은 이미지는 원본 크기를 유지하고 가운데에 놓는다.
- PSD·PSB에서 연 문서에는 가져온 이미지를 항상 캔버스의 90% 영역 안에 가운데 배치해 가장자리와 변형 손잡이가 가려지지 않게 한다. 이 문서 종류는 탭을 바꿔도 유지되고, 다른 형식으로 저장하면 새 형식에 맞게 갱신된다.
- 파일 메뉴 가져오기, 열린 캔버스로 파일 끌어놓기, 클립보드·OLE 이미지 놓기가 모두 같은 규칙을 사용한다.

Core 테스트는 첫 이미지가 빈 레이어를 교체하면서 해상도를 보존하는지와 큰 이미지의 비율 유지 축소를 확인한다. 셸 자체 검사는 실제 빈 문서 및 PSD 탭에서 전체 가져오기 경로를 확인한다.

## 21. 포토샵 문자 레이어 호환성과 내부 알림 (2026-09-24)

- 편집 가능한 문자 레이어의 `TySh` 끝 경계값을 Adobe 명세대로 4개의 8바이트 실수로 기록한다. 기존 코드는 이를 4바이트 정수로 기록해 블록 끝 16바이트가 모자랐고, 관대한 psd-tools와 자체 파서는 읽었지만 포토샵은 문자 레이어를 래스터화하고 문자 엔진을 비활성화했다.
- `Txt ` 기술자의 본문은 null 종료 문자열로, `EngineData.Editor.Text`는 마지막 문단을 닫는 캐리지 리턴까지 포함하도록 서로 다른 종료 규칙을 적용한다.
- 가져오기 파서는 `TySh`의 네 경계값까지 실제로 읽는다. Adobe의 8바이트 형식을 우선하되, 기존 psd-tools 계열 파일의 4바이트 정수 변형도 열 수 있다. 독립 검사 스크립트는 우리가 내보낸 블록이 반드시 공식 32바이트 경계로 끝나는지 원시 바이트로 확인한다.
- PSD를 열거나 저장할 때 생기는 호환성 안내는 Windows 메시지 상자 대신 프로그램 안의 모달 안내판으로 표시한다. 다른 창 뒤로 숨지 않으며 확인 버튼 하나로 닫힌다.
